<p className="dk-subheader">Import `.sql` files into your TypeScript code with full type inference</p>

Reylo lets you import `.sql` files with full type safety. It's powered by TypeScript [content mappers](https://github.com/microsoft/typescript-go/pull/4712), introduced in TypeScript 7.1 (currently [in beta](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/)), an official mechanism for integrating external file types directly into TypeScript compilation.

```ts twoslash tab="main.ts" dialect="postgres"
// @hover: getAuthor author
import postgres from "postgres";
import getAuthor from "./get_author.sql";

const db = postgres(process.env.DATABASE_URL!);

// hover over author to see its type
const author = await getAuthor.run(db, { id: 1 });
```

```sql tab="get_author.sql"
select u.id, u.name, count(p.id)::int as post_count
from users u
left join posts p on p.user_id = u.id
where u.id = :id
group by u.id
```

<div className="dk-features">

- 💪 **The full power of SQL.** Any statement your database runs, in its own dialect.
- 🌵 **DRY.** The types come from the SQL itself: no hand-written row types, no schema file to keep in sync.
- 🎯 **Checked against your database.** A misspelled column, a wrong parameter or a dropped table is a type error, in `tsc` and in your editor.
- 🤖 **Agent-friendly.** Each fact lives in one place, so an agent cannot leave a stale type behind, and the type check finds every caller it missed.
- 🧩 **Postgres, MySQL and SQLite.** Bring your own driver: `pg`, postgres.js, mysql2, better-sqlite3, Bun, Cloudflare D1 and [more](#supported-drivers).
- ⚡ **No codegen.** The type checker asks Reylo directly: no generated files, no watcher.

### Install

Reylo needs:

- **TypeScript 7.1 beta or later.** The first release with content mappers.
- **Node 24 or later, Bun or nub.**
- **A running dev database.** Reylo's type inference engine needs to know your current database schema. It does this by introspecting your live database: Postgres, MySQL 8.0.22 or later, or a SQLite file.

```sh
npm install reylo
npm install -D @reylosql/postgres  # or mysql, sqlite
npm install -D typescript@beta
```

Then set `DATABASE_URL` to your database, in the environment or in `.env`: see [`url`](#url).

### TypeScript

Add Reylo to `tsconfig.json`:

```jsonc title="tsconfig.json"
{
  "compilerOptions": { /* ... */ },
  "contentMappers": [ // [!code ++]
    { "package": "reylo", "extensions": [".sql"] } // [!code ++]
  ] // [!code ++]
}
```

Then type-check with `--runExternalCode`, which lets `tsc` run content mappers:

```jsonc title="package.json"
{
  "scripts": {
    "typecheck": "tsc --noEmit --runExternalCode" // [!code ++]
  }
}
```

<Details summary="Starting from an empty project" id="a-new-project">

A new project also needs Node's types and ES modules:

```sh
npm install -D @types/node
```

```jsonc title="tsconfig.json"
{
  "compilerOptions": {
    "module": "nodenext",
    "strict": true,
    "types": ["node"]
  },
  "contentMappers": [
    { "package": "reylo", "extensions": [".sql"] }
  ]
}
```

```json title="package.json"
{
  "type": "module"
}
```

TypeScript 7 loads `@types/node` only when `types` names it, and `"type": "module"` lets `main.ts` use a top-level `await`.

### Node

Node loads Reylo with `--import`, which turns each `.sql` import into a module as it loads, and `--env-file` loads your `.env` for the app:

```sh
node --env-file=.env --import reylo/register main.ts
```

### Plugins

Everywhere else, a plugin turns each `.sql` import into a module: Bun and nub load Reylo's preload from their config files, and a bundler builds each module at build time, so a bundled app needs no `--import` and no preload.

### `.run()`

Pass `.run()` a client and the parameters: it runs the statement and resolves to its result, shaped by how many rows Reylo proves the statement can return:

| The statement | Resolves to |
| --- | --- |
| A match on a primary or unique key, or `limit 1` | `Row \| null` |
| An aggregate without `group by`, a one-row `insert … returning` | `Row` |
| An `insert`, `update` or `delete` without `returning` | `void` |
| Anything else | `Row[]` |

At run time, a statement that resolves to `Row` throws unless it gets exactly one row, and one that resolves to `Row | null` throws when it gets more than one. The client is one from any of the [supported drivers](#supported-drivers), or a transaction, savepoint or connection taken from it. The method always returns a promise, which rejects with the driver's own error.

### `.runSync()`

On better-sqlite3, `node:sqlite` and `bun:sqlite`, `.runSync()` runs the statement synchronously and returns the result itself, so it works inside better-sqlite3's and bun:sqlite's `db.transaction(fn)`, whose function cannot await:

```ts twoslash dialect="sqlite"
import Database from "better-sqlite3";
import createUser from "./create_user.sql";
import renameUser from "./rename_user.sql";

const db = new Database("app.db");

db.transaction(() => {
  const { id } = createUser.runSync(db, { name: "Ada", email: null });
  renameUser.runSync(db, { id, name: "Ada Lovelace" });
})();
```

With `node:sqlite`, which has no `db.transaction()`, run the statements between `db.exec("begin")` and `db.exec("commit")`.

### `.with()`

Calling `.with(client)` binds the statement to a client once, such as a transaction, and returns a function that takes the parameters:

```ts twoslash
import getUser from "./get_user.sql";

const get = getUser.with(db);
const user = await get({ id: 1 });
```

### `.sql`

The statement as Reylo sends it to the database, typed as its string literal:

```ts twoslash
import getUser from "./get_user.sql";

getUser.sql;
//      ^?
```

### `.raw`

The file's contents, as written. It is the same as `.sql` except where the file uses Reylo's own syntax, which Reylo compiles for your database ([Parameters](#parameters)): a `:name` parameter becomes `$1` or `?`, a `::` cast becomes MySQL's or SQLite's own, and a JSON parameter's schema stays in Reylo.

```ts twoslash
import getUser from "./get_user.sql";

getUser.raw;
//      ^?
```

### `.inputSchema`

The JSON Schema (2020-12) of the parameters, as a plain object, for anything that takes JSON Schema: an OpenAPI document, a form, an agent's tool definition, or a library that reads [Standard Schema](https://standardschema.dev).

```ts twoslash
import getUser from "./get_user.sql";

getUser.inputSchema;
// { type: "object", properties: { id: { type: "integer", … } },
//   required: ["id"], … }
```

### `.outputSchema`

The JSON Schema of the result, as `JSON.stringify` writes it:

```ts twoslash
import getUser from "./get_user.sql";

getUser.outputSchema;
// { anyOf: [{ type: "object", properties: { id, name, email }, … },
//   { type: "null" }] }
```

## Parameters

Reylo adds a little syntax of its own to SQL, the same on Postgres, MySQL and SQLite, and compiles it to what your database runs: named parameters, `::` casts and typed JSON parameters.

### Named parameters

Write each parameter as `:name`, on every database, and `.run()` takes the values as an object. Reylo sends the statement with your database's own placeholders, `$1` on Postgres and `?` on MySQL and SQLite, and types each parameter from where the statement uses it: the column it is compared with or written to, or the function it is passed to.

### Casts

Most parameters need no cast. Where nothing in the statement types one, cast it with `::type`, which works on every database. Here only Postgres needs one:

```sql file="users_named.sql" tab="Postgres" tab-group="dialect"
select id, name from users
where name like concat(:prefix::text, '%')
```

```sql file="users_named.sql" tab="MySQL" tab-group="dialect"
select id, name from users
where name like concat(:prefix, '%')
```

```sql file="users_named.sql" tab="SQLite" tab-group="dialect"
select id, name from users
where name like :prefix || '%'
```

```ts twoslash
import usersNamed from "./users_named.sql";

const users = await usersNamed.run(db, { prefix: "Ad" });
//                                        ^?
```

Postgres's `concat` takes any type, so the cast is what types `:prefix` there; MySQL and SQLite type it from `concat` and `||`. Postgres reads `::` itself, and on MySQL and SQLite, Reylo writes it as their own cast: `:n::int` is `cast(? as signed)` on MySQL and `cast(? as integer)` on SQLite. Those casts turn a value they cannot read into 0 or `null`, so Reylo checks the value against the type before the statement runs. Each database's own `cast(… as …)` works too.

### JSON parameters

A JSON parameter carries a JSON Schema in its cast. The schema types it in TypeScript, and Reylo checks every value against it before the statement runs, so a list, a batch of rows or a nested object is one parameter:

```sql file="add_users.sql" tab="Postgres" tab-group="dialect"
with input as (
  select :names::jsonb('{
    "type": "array",
    "items": { "type": "string" }
  }') as names
)
insert into users (name)
select jsonb_array_elements_text(input.names) from input
```

```sql file="add_users.sql" tab="MySQL" tab-group="dialect"
insert into users (name)
with input as (
  select :names::json('{
    "type": "array",
    "items": { "type": "string" }
  }') as names
)
select j.name
from input, json_table(input.names, '$[*]' columns (
  name text path '$'
)) as j
```

```sql file="add_users.sql" tab="SQLite" tab-group="dialect"
with input as (
  select :names::json('{
    "type": "array",
    "items": { "type": "string" }
  }') as names
)
insert into users (name)
select j.value from input, json_each(input.names) as j
```

```ts twoslash
import addUsers from "./add_users.sql";

await addUsers.run(db, { names: ["Ada", "Grace"] });
//                       ^?
```

- The schema is JSON Schema 2020-12: `string`, `number`, `integer`, `boolean`, `null`, `object` and `array`, a key optional unless `required` lists it, and `{ "type": ["string", "null"] }` for a value that may be `null`.
- Its checks, such as `format`, `pattern`, `minimum`, `maxItems` and `enum`, run before the statement does, and a value that fails makes `.run()` reject with every issue listed. The `enum` and `const` keywords also narrow the type, and `oneOf`, `anyOf` and `allOf` make a union.

The examples use JSON parameters to [insert many rows](#insert-many-rows), [insert related rows](#insert-related-rows) and [record events of several kinds](#record-events-of-several-kinds).

## Configuration

Reylo reads its settings from `.reylo.yaml`, beside `package.json`:

```yaml title=".reylo.yaml"
url: ${DATABASE_URL}
direct_url: ${DIRECT_URL}
env: [.env.local, .env]
strict_params: true
```

Every key is optional: a project without the file behaves as if it held `url: ${DATABASE_URL}`.

### `url`

The database Reylo analyzes each statement against. The default is `${DATABASE_URL}`, and the scheme names the dialect:

```sh title=".env" tab="Postgres" tab-group="dialect"
# or postgresql://; the type check uses your pg or postgres.js
DATABASE_URL=postgres://localhost:5432/app
```

```sh title=".env" tab="MySQL" tab-group="dialect"
# or mariadb://; the type check uses your mysql2
DATABASE_URL=mysql://root@localhost:3306/app
```

```sh title=".env" tab="SQLite" tab-group="dialect"
# or sqlite:; the path starts at package.json; no driver needed
DATABASE_URL=file:./app.db
```

A `${VAR}` comes from the environment, then from the [`env`](#env) files. One that nothing sets is an error, which every `.sql` import reports. Write the URL itself, or another variable:

```yaml title=".reylo.yaml"
url: ${APP_DATABASE_URL}
```

### `direct_url`

A URL that reaches the database past a pooler. Describing a statement through a pooler in transaction mode, such as PgBouncer's, can fail, so when `direct_url` is set, Reylo's analysis (the type check and the editor) connects through it instead of `url`. It has no default, and your app's client is not affected.

```yaml title=".reylo.yaml"
url: ${DATABASE_URL}
direct_url: ${DIRECT_URL}
```

### `env`

The `.env` files Reylo reads, relative to `.reylo.yaml`. The default is `[.env.local, .env]`: the first file that sets a variable wins, and the environment wins over every file.

```yaml title=".reylo.yaml"
env: [.env.development, .env]
```

Reylo reads them for its own analysis only. Your app loads `.env` itself: Node takes `--env-file` ([Node](#node)), and Bun and nub read `.env` on their own.

### `strict_params`

With `strict_params: true`, a [parameter that nothing types](#a-parameter-nothing-types) is an error instead of `unknown`. The default is `false`.

```yaml title=".reylo.yaml"
strict_params: true
```

## How it works

Reylo is a content mapper, the kind of plugin TypeScript 7.1 introduced for files that are not TypeScript. Your `tsconfig.json` names Reylo for `.sql` files, so whenever the type checker meets a `.sql` import, in `tsc` or in your editor, it hands Reylo the file and takes back the module's types. It is TypeScript's own mechanism, so the types are the same in CI and as you type.

<HowItWorksDiagram />

To type a statement, Reylo asks your live database. It has the database prepare the statement, without running it (Postgres and MySQL on the server, SQLite in Reylo's own copy of SQLite, from the database file's schema), and reads the catalog. From the answer, Reylo learns:

- the parameter types
- the column types
- nullability, from `NOT NULL` and outer joins
- the row count, from keys, aggregates, `limit 1` and `returning`

At run time, Node's [`--import`](#node), Bun's or nub's preload, or a bundler [plugin](#plugins) turns the same file into a module that runs the statement through your driver.

Reylo keeps each answer in `.reylo/`, keyed by a fingerprint of the schema, so it asks the database again only for a schema it has not seen. After a migration, from any migration tool, the next type check sees the new schema: a statement that names a dropped or renamed column fails in its `.sql` file, and a caller that reads a column the statement no longer returns fails in TypeScript.

<Details summary="What an error looks like" id="errors">

An error in a `.sql` file is a type error at its line and column, in the type check and in the editor:

```ansi title="Terminal"

[7m1[0m select id, nmae, email
[7m [0m [91m           ~~~~[0m

Found 1 error in get_user.sql[90m:1[0m
```

A wrong argument is an error at the call site:

```ts twoslash

```

While a `.sql` file has an error, `tsc` holds back the TypeScript errors, so fix the SQL first. A build stops at the same error, and so does the preload. At run time, `.run()` rejects with the driver's own error, and with Reylo's when the rows do not fit the row count ([`.run()`](#run)).

<Details summary="In CI, and in builds without a database" id="in-ci">

A CI job that type-checks starts the database, applies the migrations, and runs `tsc --noEmit --runExternalCode` with `DATABASE_URL` set. Tests need the database too, or a filled `.reylo/`: Vitest's [Vite plugin](#setup-vite) and Jest's [transformer](#setup-jest) analyze each `.sql` file as a build does.

Every step that loads a `.sql` file (the type check, a plugin, the preload) keeps its analysis in `.reylo/`, and a later step reads it from there:

- The `.reylo/` directory is a cache with its own `.gitignore`, so git skips it.
- When the database answers, an entry made against another schema is analyzed again. An editor or a dev server checks the schema again at most every 5 seconds.
- When the database is out of reach, the entries are used as they are, and a statement that `.reylo/` lacks is an error.

So a build that cannot reach the database, such as a container build, takes the `.reylo/` that a type check filled where the database answers. Reylo keys each entry by the server it came from (scheme, user, host, port and database), or by the SQLite file's absolute path, so the build sets the same URL as the type check (`DATABASE_URL`, or [`direct_url`](#direct_url) when it is set), even though it cannot connect, and a SQLite project keeps its path.

</Details>

## Supported drivers

Reylo is bring-your-own-driver: pass `.run()` a client from any of these, or a transaction, savepoint or connection taken from one (see [Run statements in a transaction](#run-statements-in-a-transaction)). The type check reads the schema through `pg` or postgres.js on Postgres and through mysql2 on MySQL, so an app on another driver adds one of those as a dev dependency. Every driver gives Reylo's queries the same values, whatever it is set up to return for yours ([Data types](#data-types)). How Reylo reads each driver's values, the settings it refuses and what a driver loses before Reylo sees a value are on each database's page: [Postgres](/postgres#drivers), [MySQL](/mysql#drivers) and [SQLite](/sqlite#drivers).

## Data types

Reylo gives every value one type, the same on every driver, whatever the driver is set up to return: it decodes each value of its own queries itself, on your client, and leaves your other queries as your driver decodes them. A 64-bit integer is a `bigint`, a decimal its exact text, an instant the ISO 8601 text of the instant in UTC, which `Temporal.Instant.from` reads, a date or a time without a zone the text the database wrote, a truth value a `boolean`, JSON is parsed and binary data is a `Uint8Array`. ## Examples

Each example runs against [the schema at the top of the page](#schema), and calls the client `db`. A statement that differs between databases has a tab for each: pick a dialect once and every example follows it.

### List rows

A statement that can match more than one row resolves to an array.

```sql file="list_users.sql" dialect="all"
select id, name, role, tags, created_at from users
where role = :role
order by created_at desc
limit :limit
```

```ts twoslash
import listUsers from "./list_users.sql";

const users = await listUsers.run(db, { role: "member", limit: 20 });
//    ^?
```

### Count rows

An aggregate without `group by` is exactly one row.

```sql file="count_users.sql" dialect="all"
select count(*) as total from users where role = :role
```

```ts twoslash
import countUsers from "./count_users.sql";

const { total } = await countUsers.run(db, { role: "admin" });
//      ^?
```

### Filter on an optional value

A `coalesce` lets a parameter be `null`: here `null` matches every role. A parameter takes `null` only where the statement allows it, such as a `coalesce` or a nullable column it is written to.

```sql file="users_by_role.sql" dialect="all"
select id, name from users
where role = coalesce(:role, role)
```

```ts twoslash
import usersByRole from "./users_by_role.sql";

const users = await usersByRole.run(db, { role: "admin" });
//                                        ^?
```

### Sort by a chosen column

A parameter is a value, never a name: `order by :column` sorts by a constant, and `select * from :table` is a syntax error. Choose the column with `case`:

```sql file="sorted_users.sql" dialect="all"
select id, name, created_at from users
order by
  case :sort when 'name' then name end,
  created_at desc
```

```ts twoslash
import sortedUsers from "./sorted_users.sql";

const users = await sortedUsers.run(db, { sort: "name" });
//    ^?
```

### Search several columns

Each parameter appears once in a statement, so that one place types it, and a second use is an error. To use a value twice, select it once in a `with`:

```sql file="search_users.sql" tab="Postgres" tab-group="dialect"
with input as (
  select concat('%', :q::text, '%') as pattern
)
select id, name from users, input
where name like input.pattern or email like input.pattern
```

```sql file="search_users.sql" tab="MySQL" tab-group="dialect"
with input as (
  select concat('%', :q, '%') as pattern
)
select id, name from users, input
where name like input.pattern or email like input.pattern
```

```sql file="search_users.sql" tab="SQLite" tab-group="dialect"
with input as (
  select concat('%', :q, '%') as pattern
)
select id, name from users, input
where name like input.pattern or email like input.pattern
```

```ts twoslash
import searchUsers from "./search_users.sql";

const users = await searchUsers.run(db, { q: "ada" });
//    ^?
```

### Join tables

A column of the table a `left join` adds can be `null`, and a `coalesce` gives it a default.

```sql file="user_posts.sql" dialect="all"
select u.name, p.title, coalesce(p.title, '') as label
from users u
left join posts p on p.user_id = u.id
```

```ts twoslash
import userPosts from "./user_posts.sql";

const rows = await userPosts.run(db);
//    ^?
```

### Page through rows

Pass the sort key of the last row you have, here `created_at` and `id`, to get the rows after it.

```sql file="next_page.sql" dialect="all"
select id, name, created_at from users
where (created_at, id) < (:created_at, :id)
order by created_at desc, id desc
limit 20
```

### Keep a list's order

Number the list's elements, and sort by the number.

```sql file="users_in_order.sql" tab="Postgres" tab-group="dialect"
-- with ordinality numbers the elements
select u.id, u.name
from unnest(:ids::int[]) with ordinality as i(id, position)
join users u on u.id = i.id
order by i.position
```

```sql file="users_in_order.sql" tab="MySQL" tab-group="dialect"
-- a for ordinality column numbers the elements
with input as (
  select :ids::json('{
    "type": "array",
    "items": { "type": "integer" }
  }') as ids
)
select u.id, u.name
from input, json_table(input.ids, '$[*]' columns (
  position for ordinality,
  id int path '$'
)) as i
join users u on u.id = i.id
order by i.position
```

```sql file="users_in_order.sql" tab="SQLite" tab-group="dialect"
-- json_each numbers the elements as key
with input as (
  select :ids::json('{
    "type": "array",
    "items": { "type": "integer" }
  }') as ids
)
select u.id, u.name
from input, json_each(input.ids) as i
join users u on u.id = i.value
order by i.key
```

### Nest related rows

Build the related rows as JSON in the statement. Reylo types the JSON from the arguments that build it.

```sql file="user_with_posts.sql" tab="Postgres" tab-group="dialect"
select u.id, u.name,
  coalesce((
    select jsonb_agg(jsonb_build_object(
      'id', p.id,
      'title', p.title,
      'at', p.published_at
    ))
    from posts p where p.user_id = u.id
  ), '[]') as posts
from users u
where u.id = :id
```

```sql file="user_with_posts.sql" tab="MySQL" tab-group="dialect"
select u.id, u.name,

      'id', p.id,
      'title', p.title,
      'at', p.published_at
    ))
    from posts p where p.user_id = u.id
  ), json_array()) as posts
from users u
where u.id = :id
```

```sql file="user_with_posts.sql" tab="SQLite" tab-group="dialect"
select u.id, u.name,

      'id', p.id,
      'title', p.title,
      'at', p.published_at
    ))
    from posts p where p.user_id = u.id
  ) as posts
from users u
where u.id = :id
```

### Insert related rows

Users with their posts, in one parameter. The posts find their user by `email`, a unique key.

<DialectTabs>
<Dialect value="Postgres">

Postgres writes both tables in one statement: a `with` inserts the users, and the statement inserts the posts.

```sql file="create_users_with_posts.sql"
with input as (
  select :users::jsonb('{
    "type": "array",
    "items": {
      "type": "object",
      "properties": {
        "name": { "type": "string" },
        "email": { "type": "string", "format": "email" },
        "posts": {
          "type": "array",
          "items": {
            "type": "object",
            "properties": { "title": { "type": "string" } },
            "required": ["title"]
          }
        }
      },
      "required": ["name", "email", "posts"]
    }
  }') as users
),
new_users as (
  insert into users (name, email)
  select u.name, u.email
  from input, jsonb_to_recordset(input.users) as u(name text, email text)
  returning id, email
)
insert into posts (user_id, title)
select n.id, p.title
from input
cross join jsonb_to_recordset(input.users) as u(email text, posts jsonb)
join new_users n on n.email = u.email
cross join jsonb_to_recordset(u.posts) as p(title text)
```

```sql title="insert_posts.sql"
insert into posts (user_id, title)
with input as (
  select :users::json('{
    "type": "array",
    "items": {
      "type": "object",
      "properties": {
        "email": { "type": "string" },
        "posts": {
          "type": "array",
          "items": {
            "type": "object",

          }

      "required": ["email", "posts"]
    }

select users.id, u.title
from input, json_table(input.users, '$[*]' columns (
  -- the collation of users.email
  email varchar(255) collate utf8mb4_0900_ai_ci path '$.email',

where u.title is not null
```

```ts twoslash
const db = mysql.createPool(process.env.DATABASE_URL!);

  {
    name: "Ada",
    email: "ada@example.com",
    posts: [{ title: "Notes" }],
  },
];

const conn = await db.getConnection();
try {
  await conn.beginTransaction();
  await insertUsers.run(conn, { users });
  await insertPosts.run(conn, { users });
  await conn.commit();

  await conn.rollback();
  throw error;
} finally {
  conn.release();
}
```

### Run statements in a transaction

A transaction, a savepoint or a connection taken from a client is a client too:

<DialectTabs>
<Dialect value="Postgres">

```ts twoslash
import postgres from "postgres";
import getUser from "./get_user.sql";
import renameUser from "./rename_user.sql";

const db = postgres(process.env.DATABASE_URL!);

await db.begin(async (tx) => {
  const user = await getUser.run(tx, { id: 1 });
  await tx.savepoint((sp) =>
    renameUser.run(sp, { id: user!.id, name: "Grace" }),
  );
});
```

</Dialect>
<Dialect value="MySQL">

```ts twoslash
import mysql from "mysql2/promise";
import renameUser from "./rename_user.sql";

const db = mysql.createPool(process.env.DATABASE_URL!);

const conn = await db.getConnection();
try {
  await conn.beginTransaction();
  await renameUser.run(conn, { id: 1, name: "Grace" });
  await conn.commit();
} catch (error) {
  await conn.rollback();
  throw error;
} finally {
  conn.release();
}
```

</Dialect>
<Dialect value="SQLite">

On better-sqlite3, `node:sqlite` and `bun:sqlite`, `.runSync()` runs the statement synchronously, so it works inside better-sqlite3's and bun:sqlite's `db.transaction(fn)`, whose function cannot await. With `node:sqlite`, which has no `db.transaction()`, run the statements between `db.exec("begin")` and `db.exec("commit")`.

```ts twoslash
import Database from "better-sqlite3";

import renameUser from "./rename_user.sql";

const db = new Database("app.db");

db.transaction(() => {
  const { id } = createUser.runSync(db, { name: "Ada", email: null });
  renameUser.runSync(db, { id, name: "Ada Lovelace" });
})();
```

</Dialect>
