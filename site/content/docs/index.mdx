<p className="reylo-subheader">Import `.sql` files into your TypeScript code with full type inference</p>

Reylo lets you import `.sql` files with full type safety. It's powered by TypeScript [content mappers](https://github.com/microsoft/typescript-go/pull/4712), introduced in TypeScript 7.1 (currently [in beta](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/)), an official mechanism for integrating external file types directly into TypeScript compilation.

```ts twoslash tab="main.ts" dialect="postgres"
// @hover: getAuthor author
import postgres from "postgres";
import getAuthor from "./get_author.sql";

const db = postgres(process.env.DATABASE_URL!);

// hover over author to see its type
const author = await getAuthor.run(db, { id: 1 });
```

```sql tab="get_author.sql"
select u.id, u.name, count(p.id)::int as post_count
from users u
left join posts p on p.user_id = u.id
where u.id = :id
group by u.id
```

### Install

Reylo needs:

- **TypeScript 7.1 beta or later.** The first release with content mappers.
- **Node 24 or later, Bun or nub.**
- **A running dev database.** Reylo's type inference engine needs to know your current database schema. It does this by introspecting your live database: Postgres, MySQL 8.0.22 or later, or a SQLite file.

```sh
npm install reylo
npm install -D typescript@beta
```

Then set `DATABASE_URL` to your database, in the environment or in `.env`: see [`url`](#url).

### TypeScript

Add Reylo to `tsconfig.json`:

```jsonc title="tsconfig.json"
{
  "compilerOptions": { /* ... */ },
  "contentMappers": [ // [!code ++]
    { "package": "reylo", "extensions": [".sql"] } // [!code ++]
  ] // [!code ++]
}
```

Type-check with `--runExternalCode`, which lets `tsc` run content mappers. Without it, `tsc` reports TS18068 and finds no `.sql` module (TS2307).

```json title="package.json"
{
  "scripts": {
    "typecheck": "tsc --noEmit --runExternalCode"
  }
}
```

<span id="one-statement-per-file" />

A `.sql` file holds one `select`, `insert`, `update`, `delete` or `values`; `merge` on Postgres; `replace` on MySQL and SQLite; or `table` on Postgres and MySQL. The type check reports every other `.sql` file it reads, imported or not, such as a migration or a schema, so keep those out of `tsconfig.json`:

```jsonc title="tsconfig.json"
{
  "compilerOptions": { /* ... */ },
  "contentMappers": [ /* ... */ ],
  "exclude": ["db/**"] // [!code ++]
}
```

`reylo generate` skips such files, and only the type check reports them: the plugins and the preload build whatever you import.

A new project also needs Node's types and ES modules:

```sh
npm install -D @types/node
```

```jsonc title="tsconfig.json"
{
  "compilerOptions": {
    "module": "nodenext",
    "strict": true,
```

### Node

Node loads Reylo with `--import`, which turns each `.sql` import into a module as it loads, and `--env-file` loads your `.env` for the app:

```sh
node --env-file=.env --import reylo/register main.ts
```

### Plugins

Everywhere else, a plugin turns each `.sql` import into a module: Bun and nub load Reylo's preload from their config files, and a bundler builds each module at build time, so a bundled app needs no `--import` and no preload.

<Accordions type="multiple">
<Accordion title="Bun" id="setup-bun">

Bun takes the preload in `bunfig.toml`, so `bun main.ts` needs no flag, and loads `.env` itself:

```toml title="bunfig.toml"
preload = ["reylo/register"]
```

Bun's bundler takes the esbuild plugin:

```ts title="build.ts"

  entrypoints: ["main.ts"],
  target: "bun",
  plugins: [reylo()],
  outdir: "dist",

```

```sql title="get_user.sql" tab="Postgres" tab-group="dialect"
select id, name, email from users where id = :id
```

```sql title="get_user.sql" tab="MySQL" tab-group="dialect"
select id, name, email from users where id = :id
```

```sql title="get_user.sql" tab="SQLite" tab-group="dialect"
select id, name, email from users where id = :id
```

### `run`

`run(client, params)` runs the statement and resolves to its result, shaped by how many rows Reylo proves the statement can return:

| The statement | `cardinality` | `run` resolves to |
| --- | --- | --- |
| A match on a primary or unique key, or `limit 1` | `maybeOne` | `Row \| null` |
| An aggregate without `group by`, a one-row `insert … returning` | `one` | `Row` |
| An `insert`, `update` or `delete` without `returning` | `none` | `void` |
| Anything else | `many` | `Row[]` |

At run time, a `one` query throws unless it gets exactly one row, and a `maybeOne` query throws when it gets more than one. The client is one from any of the [supported drivers](#supported-drivers), or a transaction, savepoint or connection taken from it, and `run` always returns a promise, which rejects with the driver's own error. The parameters may also be an array, in the order of [`params`](#params):

```ts twoslash title="main.ts"
import getUser from "./get_user.sql";

const user = await getUser.run(db, [1]);
```


### `runSync`

On better-sqlite3, `node:sqlite` and `bun:sqlite`, `runSync` runs the statement synchronously and returns the result itself, so it works inside better-sqlite3's and bun:sqlite's `db.transaction(fn)`, whose function cannot await:

```ts twoslash title="main.ts" dialect="sqlite"
import Database from "better-sqlite3";
import createUser from "./create_user.sql";
import renameUser from "./rename_user.sql";

const db = new Database("app.db");

db.transaction(() => {
  const { id } = createUser.runSync(db, { name: "Ada", email: null });
  renameUser.runSync(db, { id, name: "Ada Lovelace" });
})();
```

`node:sqlite` has no `db.transaction`: run the statements between `db.exec("begin")` and `db.exec("commit")`.

### `with`

`with(client)` binds the statement to a client once, such as a transaction, and returns a function that takes the parameters:

```ts twoslash title="main.ts"
import getUser from "./get_user.sql";

const get = getUser.with(db);
const user = await get({ id: 1 });
```

### `sql`

The statement as Reylo sends it to the database, typed as its string literal:

```ts twoslash title="main.ts"
import getUser from "./get_user.sql";

getUser.sql;
//      ^?
```

### `raw`

The file's contents, as written:

```ts twoslash title="main.ts"
import getUser from "./get_user.sql";

getUser.raw;
//      ^?
```

### `params`

The parameters' names, in the order an array of values follows. A query also carries its row count, `cardinality`, and its `dialect`:

```ts twoslash title="main.ts"
import getUser from "./get_user.sql";

getUser.params;       // ["id"]
getUser.cardinality;  // "maybeOne"
```

### `inputSchema`

The JSON Schema (2020-12) of the parameters, as a plain object, for anything that takes JSON Schema: an OpenAPI document, a form, an agent's tool definition.

```ts twoslash title="main.ts"
import getUser from "./get_user.sql";

getUser.inputSchema;
// { type: "object", properties: { id: { type: "integer", … } }, required: ["id"], … }
```

### `outputSchema`

The JSON Schema of the result, as `JSON.stringify` writes it:

```ts twoslash title="main.ts"
import getUser from "./get_user.sql";

getUser.outputSchema;
// { anyOf: [{ type: "object", properties: { id, name, email }, … }, { type: "null" }] }
```

A query is also a [Standard JSON Schema](https://standardschema.dev), so a library that reads one gets both schemas from `getUser["~standard"].jsonSchema`.

## Parameters

Each `:name` in a statement is a parameter, and `run` takes them as an object. Reylo types each one from where the statement uses it: the column it is compared with or written to, or the function it is passed to.

### Casts

Most parameters need no cast. Where nothing types one, cast it, with `::type` on every dialect or with the dialect's own `cast(… as …)`. Here only Postgres needs one:

```sql title="users_named.sql" tab="Postgres" tab-group="dialect"
select id, name from users
where name like concat(:prefix::text, '%')
```

```sql title="users_named.sql" tab="MySQL" tab-group="dialect"
select id, name from users
where name like concat(:prefix, '%')
```

```sql title="users_named.sql" tab="SQLite" tab-group="dialect"
select id, name from users
where name like :prefix || '%'
```

```ts twoslash title="main.ts"
import usersNamed from "./users_named.sql";

const users = await usersNamed.run(db, { prefix: "Ad" });
//                                        ^?
```

<DialectTabs follow>
<Dialect value="Postgres">

`concat` takes any type, so the cast types `:prefix`.

</Dialect>
<Dialect value="MySQL">

MySQL types `:prefix` from `concat`, which takes strings, so it needs no cast.

</Dialect>
<Dialect value="SQLite">

SQLite types `:prefix` from `||`, which joins strings, so it needs no cast.

</Dialect>
</DialectTabs>

On MySQL and SQLite, Reylo writes `::type` as the dialect's own cast: `:n::int` is `cast(? as signed)` on MySQL and `cast(? as integer)` on SQLite. Their casts turn a value they cannot read into 0 or `null`, so Reylo checks the value against the type before the statement runs.

### `null`

A parameter takes `null` where the statement lets it be null: a nullable column it is written to, as `email` in `create_user.sql` above, or a `coalesce`, as in [Filter on an optional value](#filter-on-an-optional-value).

### Lists

<DialectTabs follow>
<Dialect value="Postgres">

A Postgres array parameter takes a JavaScript array, as in `where id = any(:ids)` ([Filter by a list](#filter-by-a-list)).

</Dialect>
<Dialect value="MySQL">

### JSON parameters

A JSON parameter carries a JSON Schema in its cast. The schema types it in TypeScript, and Reylo checks every value against it before the statement runs, so a list, a batch of rows or a nested object is one parameter:

```sql title="add_users.sql" tab="Postgres" tab-group="dialect"
with input as (
  select :names::jsonb('{ "type": "array", "items": { "type": "string" } }') as names
)
insert into users (name)
select jsonb_array_elements_text(input.names) from input
```

```sql title="add_users.sql" tab="MySQL" tab-group="dialect"
insert into users (name)
with input as (
  select :names::json('{ "type": "array", "items": { "type": "string" } }') as names
)
select j.name
from input, json_table(input.names, '$[*]' columns (name text path '$')) as j
```

```sql title="add_users.sql" tab="SQLite" tab-group="dialect"
with input as (
  select :names::json('{ "type": "array", "items": { "type": "string" } }') as names
)
insert into users (name)
select j.value from input, json_each(input.names) as j
```

```ts twoslash title="main.ts"
import addUsers from "./add_users.sql";

await addUsers.run(db, { names: ["Ada", "Grace"] });
//                       ^?
```

- The schema is JSON Schema 2020-12: `string`, `number`, `integer`, `boolean`, `null`, `object` and `array`, a key optional unless `required` lists it, and `{ "type": ["string", "null"] }` for a value that may be `null`.
- Its checks, such as `format`, `pattern`, `minimum`, `maxItems` and `enum`, run before the statement does, and a value that fails makes `run` reject with every issue listed. `enum` and `const` also narrow the type, and `oneOf`, `anyOf` and `allOf` make a union.
- The schema stays in Reylo: the database receives the value as JSON text, `$1::jsonb` on Postgres, `cast(? as json)` on MySQL and `?` on SQLite.

The examples use JSON parameters to [insert many rows](#insert-many-rows), [insert related rows](#insert-related-rows) and [record events of several kinds](#record-events-of-several-kinds).

### Positional parameters

A statement may use its database's own positional form instead of `:name`: `$1` on Postgres, `?` on MySQL, `?1` on SQLite. The key is then the number, as in `{ 1: 42 }`.

## Configuration

Reylo's settings go in `.reylo.yaml`, beside `package.json`, or in the file the `REYLO_CONFIG` variable names; `tsconfig.json` only names the content mapper.

Every key is optional: a project without the file behaves as if it held `url: ${DATABASE_URL}`. A key Reylo does not know is an error at its line and column, reported on every `.sql` import; Reylo ignores a top-level `$schema` and the `api` section, which is Reylo Framework's.

### `url`

The database Reylo analyzes each statement against. The default is `${DATABASE_URL}`, and the scheme names the dialect:

```sh title=".env" tab="Postgres" tab-group="dialect"
# or postgresql://; the type check uses your pg or postgres.js
DATABASE_URL=postgres://localhost:5432/app
```

```sh title=".env" tab="MySQL" tab-group="dialect"
# or mariadb://; the type check uses your mysql2
DATABASE_URL=mysql://root@localhost:3306/app
```

```sh title=".env" tab="SQLite" tab-group="dialect"
# or sqlite:; the path starts at package.json; no driver needed
DATABASE_URL=file:./app.db
```

A `${VAR}` comes from the environment, then from the [`env`](#env) files. One that nothing sets is an error, which every `.sql` import reports. Write the URL itself, or another variable:

```yaml title=".reylo.yaml"
url: ${APP_DATABASE_URL}
```

### `direct_url`

A URL that reaches the database past a pooler. Describing a statement through a pooler in transaction mode, such as PgBouncer's, can fail, so when `direct_url` is set, Reylo's analysis (the type check, the editor and `reylo generate`) connects through it instead of `url`, and keys `.reylo/` by it. It has no default, and your app's client is not affected.

```yaml title=".reylo.yaml"
url: ${DATABASE_URL}
direct_url: ${DIRECT_URL}
```

### `env`

The `.env` files Reylo reads, relative to `.reylo.yaml`. The default is `[.env.local, .env]`: the first file that sets a variable wins, and the environment wins over every file.

```yaml title=".reylo.yaml"
env: [.env.development, .env]
```

Reylo reads them for its own analysis only. Your app loads `.env` itself: Node takes `--env-file` ([Node](#node)), and Bun and nub read `.env` on their own.

### `strict`

With `strict: true`, an [untyped parameter](#a-parameter-nothing-types) is an error instead of `unknown`. The default is `false`.

```yaml title=".reylo.yaml"
strict: true
```

### `cli`

The `.sql` files `reylo generate` analyzes, the command that fills `.reylo/` ahead of a build without a database ([In CI](#in-ci)). The globs are relative to `.reylo.yaml`: `include` replaces the default, every `.sql` file, and `exclude` adds to what is always left out: `node_modules`, build output, directories whose names start with a dot, and what git ignores. The type check reads the files `tsconfig.json` includes instead.

```yaml title=".reylo.yaml"
cli:
  include: ["src/**/*.sql"]
  exclude: ["src/legacy/**"]
```

## How it works

Reylo is a content mapper, the kind of plugin TypeScript 7.1 introduced for files that are not TypeScript. Your `tsconfig.json` names Reylo for `.sql` files, so whenever the type checker meets a `.sql` import, in `tsc` or in your editor, it hands Reylo the file and takes back the module's types. It is TypeScript's own mechanism, so the types are the same in CI and as you type.

<HowItWorksDiagram />

To type a statement, Reylo asks your live database. It has the database prepare the statement, without running it (Postgres and MySQL on the server, SQLite in Reylo's own copy of SQLite, from the database file's schema), and reads the catalog. From the answer, Reylo learns:

- the parameter types
- the column types
- nullability, from `NOT NULL` and outer joins
- the row count, from keys, aggregates, `limit 1` and `returning`

At run time, Node's [`--import`](#node), Bun's or nub's preload, or a bundler [plugin](#plugins) turns the same file into a module that runs the statement through your driver.

Reylo keeps each answer in `.reylo/`, keyed by a fingerprint of the schema, so it asks the database again only for a schema it has not seen. After a migration, from any migration tool, the next type check sees the new schema: a statement that names a dropped or renamed column fails in its `.sql` file, and a caller that reads a column the statement no longer returns fails in TypeScript.

<Details summary="In CI, and in builds without a database" id="in-ci">

A CI job that type-checks starts the database, applies the migrations, and runs `tsc --noEmit --runExternalCode` with `DATABASE_URL` set. Tests need the database too, or a filled `.reylo/`: Vitest's [Vite plugin](#setup-vite) and Jest's [transformer](#setup-jest) analyze each `.sql` file as a build does.

Every step that loads a `.sql` file (the type check, a plugin, the preload) keeps its analysis in `.reylo/`, and a later step reads it from there:

- `.reylo/` is a cache with its own `.gitignore`, so git skips it.
- When the database answers, an entry made against another schema is analyzed again. An editor or a dev server checks the schema again at most every 5 seconds.
- When the database is out of reach, the entries are used as they are, and a statement that `.reylo/` lacks is an error.

So where the build cannot reach the database, such as a container build, run `reylo generate` where it can, which fills `.reylo/` and writes no code, and carry `.reylo/` to the build:

```text
$ reylo generate
postgres at localhost/reylo_docs (DATABASE_URL in .env)
  src/admin/find_by_email.sql  ✗
  src/admin/set_email.sql      ✓
  src/queries/count_users.sql  ✓
  src/queries/create_user.sql  ✓
  src/queries/get_user.sql     ✓
  src/queries/list_users.sql   ✓

src/admin/find_by_email.sql:1:12: column "nmae" does not exist (42703)
  1 | select id, nmae
    |            ^^^^

Skipped 1 file that is not one query (a migration?): db/schema.sql

✗ 1 of 6 queries failed (0.1 s)
```

`reylo generate` reads every `.sql` file under the given paths, the current directory by default. It skips `node_modules`, build output, dot directories and what git ignores; the [`cli`](#cli) keys of `.reylo.yaml` change the set. `--force` asks the database again for every statement. The exit code is 1 when a query fails.

Reylo keys each entry by the server it came from (scheme, user, host, port and database), or by the SQLite file's absolute path. So the build sets the same URL as the place where `reylo generate` ran (`DATABASE_URL`, or [`direct_url`](#direct_url) when it is set), even though it cannot connect, and a SQLite project keeps its path.

</Details>

## Data types

Reylo gives every value one type, the same on every driver, whatever the driver is set up to return: it decodes each value of its own queries itself, on your client, and leaves your other queries as your driver decodes them. A 64-bit integer and a decimal are their exact text, an instant is a `Date`, a date or a time without a zone is the text the database wrote, JSON is parsed and binary data is a `Uint8Array`.

<Details summary="How Reylo decodes on each driver">

Each driver reads the database's protocol as it always does; Reylo makes only the choice per type that follows, for its own query, on the client you pass. A parser or option you set for your own queries does not reach Reylo's, and none of Reylo's reaches yours.

- `pg`, pg-promise, Neon and `@vercel/postgres` take a decoder table with each query, and Reylo's answers every type. PGlite takes one too, naming the statement's types.
- postgres.js hands Reylo each value's text (`.raw()`), and Reylo builds the row with the query's own column names, so a `transform` that renames your columns does not rename Reylo's.
- mysql2 takes Reylo's options with each query (`execute`), mariadb every option, and PlanetScale Reylo's `cast`.
- better-sqlite3, `node:sqlite` and `bun:sqlite` run a statement Reylo prepares once per database, with its own integer setting, whatever the database's.
- Bun.sql, libSQL, D1, `sqlite3` and `sqlite` take nothing per query, and Reylo converts the values they give.

Reylo refuses what would change its values and that it cannot undo: a `pg` client set up with `binary: true`, a pg-promise database whose `receive` event rewrites results, and a postgres.js client with a `transform.row`.

</Details>

<Details summary="What a driver loses before Reylo sees the value">

- Bun.sql keeps a `timestamp`'s and a `DATETIME`'s milliseconds, not their microseconds, writes no fraction digits that are all zero, drops a `TIME`'s fraction, and throws on a `NULL` inside an `int4[]` or a `float4[]`.
- A `real` (`float4`) or a MySQL `FLOAT` is a 32-bit float: a driver that reads the binary protocol (Bun.sql, mysql2) gives its exact value, `1.100000023841858`, and one that reads the database's text gives the shorter text's, `1.1`.
- `sqlite3`, `sqlite`, Cloudflare D1, and Bun.sql without `safeIntegers` round an integer past 2^53 before Reylo sees it, so Reylo refuses it; libSQL at its default `intMode` refuses it itself. With libSQL's `intMode: "string"`, an integer in a column with no type is its digits.
- JSON is parsed by `JSON.parse`, so an integer past 2^53 inside a document is rounded, on every driver.

</Details>

<Details summary="Binary, date and JSON values, in and out">

- A `Buffer`, which several drivers return for binary data, is a `Uint8Array`.
- A binary parameter takes a `Uint8Array`, a `Buffer` or not, on every driver: mariadb, which writes any other value as JSON, gets it from Reylo as a `Buffer`.
- On Postgres, an array parameter takes a JavaScript array on every driver, for a SQL array (`any(:ids)`, `:tags::text[]`) and for JSON (`:data::jsonb`) alike: Reylo writes it in the form the driver binds right.
- A `timestamptz` parameter takes a `Date`, or a string that names its zone: `"2026-10-12T19:06:48Z"`, `"2026-10-12 19:06:48+09"`, `"2026-10-12 19:06:48 Asia/Tokyo"`. A `timestamp` or `date` parameter, and on MySQL a `DATETIME`, `TIMESTAMP` or `DATE` one, has no zone and takes the wall-clock text, `"2026-10-12 19:06:48"` or `"2026-10-12"`, which is also what Reylo returns for such a column: drivers write a `Date`'s time in different zones, the app's, the server's or UTC, so Reylo refuses one before the statement runs.
- A parameter the statement reads as JSON (`:data::jsonb`, `cast(:data as json)`, a `json` column) takes any JSON value, and the database receives its JSON text on every driver: a string is a JSON string, so `'{"a":1}'` is stored as the string `"{\"a\":1}"`, not as an object. To pass JSON text you already hold, cast it from text: `:data::text::jsonb`.
- Inside nested JSON the database writes each value as JSON: a `bigint` is a number there and a date its text.

</Details>

When the email already exists, the insert updates that row instead. With `returning`, it resolves to the id of the row it wrote.

```sql title="upsert_user.sql" tab="Postgres" tab-group="dialect"
insert into users (name, email) values (:name, :email)
on conflict (email) do update set name = excluded.name
returning id
```

```sql title="upsert_user.sql" tab="MySQL" tab-group="dialect"
insert into users (name, email) values (:name, :email) as new
on duplicate key update name = new.name
```

```sql title="upsert_user.sql" tab="SQLite" tab-group="dialect"
insert into users (name, email) values (:name, :email)
on conflict (email) do update set name = excluded.name
returning id
```

### Record events of several kinds

`oneOf` types a JSON parameter as a union. Here a `const` key tells the members apart:

```sql title="record_events.sql" tab="Postgres" tab-group="dialect"
with input as (
  select :events::jsonb('{
    "type": "array",
    "items": {
      "oneOf": [
        {
          "type": "object",
          "properties": {
            "kind": { "type": "string", "const": "click" },
            "x": { "type": "integer" },
            "y": { "type": "integer" }
          },
          "required": ["kind", "x", "y"]
        },
        {
          "type": "object",
          "properties": {
            "kind": { "type": "string", "const": "key" },
            "code": { "type": "string" }
          },
          "required": ["kind", "code"]
        }
      ]
    }
  }') as events
)
insert into events (kind, payload)
select e.value ->> 'kind', e.value
from input, jsonb_array_elements(input.events) as e(value)
```
