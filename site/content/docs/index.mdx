Reylo types the SQL you import: write a statement in a `.sql` file, import it from TypeScript, and run it on Postgres, MySQL or SQLite. Every type comes from the statement itself, so nothing is written twice, and you keep *the full expressive power of your SQL dialect*.

<p className="reylo-lede">It's powered by TypeScript's [_content mappers_](https://github.com/microsoft/typescript-go/pull/4712) (introduced in typescript@7.1). Reylo asks your running database what each statement takes and returns, so every query has _full static types_, in the type check and in the editor.</p>

```ts twoslash tab="main.ts" dialect="postgres"
import postgres from "postgres";
import getUser from "./get_user.sql";

const db = postgres(process.env.DATABASE_URL!);

const user = await getUser.run(db, { id: 1 });
```

```sql tab="get_user.sql"
select id, name, email from users where id = :id
```

Hover over `user` to see its type.

## How it works

The type check and the editor run Reylo as a content mapper: TypeScript hands it each `.sql` file of the project, and Reylo returns the query's types. At run time, a preload or a bundler plugin turns the same file into a module.

```text
get_user.sql  →  Reylo  →  your database
  →  { id: number; name: string; email: string | null } | null
```

To type a statement, Reylo has your database prepare it, without running it: Postgres and MySQL on the server, SQLite in Reylo's own copy of SQLite, from the database file's schema. From the answer and the catalog, Reylo learns:

- the parameter types
- the column types
- nullability, from `NOT NULL` and outer joins
- the row count, from primary and unique keys

Reylo keeps each answer in `.reylo/`, and asks again [when the schema changes](#when-the-schema-changes).

## Setup

Install Reylo and point it at your database, then add it to each tool that loads your code.

### Install

```sh
npm install reylo
npm install -D typescript@next   # content mappers are in the TypeScript 7.1 dev builds
```

Reylo needs Node 24 or later. Then set `DATABASE_URL` to your database, in the environment or in `.env`: see [`url`](#url).

### TypeScript

Add Reylo to `tsconfig.json`:

```jsonc title="tsconfig.json"
{
  "compilerOptions": { /* ... */ },
  "contentMappers": [ // [!code ++]
    { "package": "reylo", "extensions": [".sql"] } // [!code ++]
  ] // [!code ++]
}
```

Type-check with `--runExternalCode`. Without the flag, `tsc` reports error TS100024 and finds no `.sql` module (TS2307).

```json title="package.json"
{
  "scripts": {
    "typecheck": "tsc --noEmit --runExternalCode"
  }
}
```

<Details summary="Starting from an empty project" id="a-new-project">

A new project also needs Node's types and ES modules:

```sh
npm install -D @types/node
```

```jsonc title="tsconfig.json"
{
  "compilerOptions": {
    "module": "nodenext",
    "strict": true,
    "types": ["node"]
  },

    { "package": "reylo", "extensions": [".sql"] }
```

### Runtimes

A preload turns each `.sql` import into a module as it loads. Node takes it with `--import`, and `--env-file` loads your `.env` for the app:

```sh
node --env-file=.env --import reylo/register main.ts
```

Bun and nub read the preload from their config files and load `.env` themselves, so `bun main.ts` and `nub main.ts` need no flag. Without the preload, Bun imports a `.sql` file as its path, with no error.

```toml title="bunfig.toml"
preload = ["reylo/register"]
```

```jsonc title="nub.jsonc"
{
  "preload": ["reylo/register"]
}
```

### Bundlers and frameworks

A bundler plugin turns each `.sql` import into a module at build time, so a bundled app needs no preload.

<Details summary="Vite" id="setup-vite">

```ts title="vite.config.ts"

import reylo from "reylo/vite";

export default defineConfig({
  plugins: [reylo()],
});
```

Import `.sql` files from server code only: the module holds the statement, and the plugin does not keep it out of a browser bundle. Vitest needs only this plugin.

</Details>
<Details summary="Next.js" id="setup-nextjs">

Reylo runs in both of Next.js's bundlers, Turbopack and webpack, on the server only.

```ts title="next.config.ts"

  typescript: { ignoreBuildErrors: true }, // the build script runs the type check first
  turbopack: {
    rules: {
      "*.sql": {
        condition: { not: "browser" },
        loaders: ["reylo/webpack-loader"],
        as: "*.js",
      },
    },
  },
  webpack(config, { isServer }) {
    if (isServer) {
      config.module.rules.push({ test: /\.sql$/, use: "reylo/webpack-loader" });
    }
    return config;
  },
};

export default nextConfig;
```

```json title="package.json"
}
```

A client component that imports a `.sql` file fails the build, so the statement never reaches the browser. On the edge runtime, use a driver that needs no TCP socket.

## Configuration

Reylo's settings go in `.reylo.yaml`, beside `package.json`, or in the file the `REYLO_CONFIG` variable names. Every key is optional: a project without the file behaves as if it held `url: ${DATABASE_URL}`. A key Reylo does not know is an error at its line and column, which every `.sql` import reports. Reylo Framework's settings go under `api`, which Reylo leaves alone. A top-level `$schema` is ignored, and Reylo takes no options in `tsconfig.json`.

### `url`

The database Reylo analyzes each statement against. The default is `${DATABASE_URL}`, and the scheme names the dialect:

```sh title=".env" tab="Postgres" tab-group="dialect"
# or postgresql://; the type check uses your pg or postgres.js
DATABASE_URL=postgres://localhost:5432/app
```

```sh title=".env" tab="MySQL" tab-group="dialect"
# or mariadb://; the type check uses your mysql2
DATABASE_URL=mysql://root@localhost:3306/app
```

```sh title=".env" tab="SQLite" tab-group="dialect"
# or sqlite:; the path starts at package.json; no driver needed
DATABASE_URL=file:./app.db
```

A `${VAR}` comes from the environment, then from the [`env`](#env) files. One that nothing sets is an error, which every `.sql` import reports. Write the URL itself, or another variable:

```yaml title=".reylo.yaml"
url: ${APP_DATABASE_URL}
```

### `direct_url`

A URL that reaches the database past a pooler. Describing a statement through a pooler in transaction mode, such as PgBouncer's, can fail, so when `direct_url` is set, Reylo's analysis (the type check, the editor and `reylo generate`) connects through it instead of `url`, and keys `.reylo/` by it. It has no default, and your app's client is not affected.

```yaml title=".reylo.yaml"
url: ${DATABASE_URL}
direct_url: ${DIRECT_URL}
```

### `env`

The `.env` files Reylo reads, relative to `.reylo.yaml`. The default is `[.env.local, .env]`: the first file that sets a variable wins, and the environment wins over every file.

```yaml title=".reylo.yaml"
env: [.env.development, .env]
```

Reylo reads them for its own analysis only. Your app loads `.env` itself: Node takes `--env-file` ([Runtimes](#runtimes)), and Bun and nub read `.env` on their own.

### `strict`

With `strict: true`, an [untyped parameter](#a-parameter-nothing-types) is an error instead of `unknown`. The default is `false`.

```yaml title=".reylo.yaml"
strict: true
```

### `types`

What your driver returns for the values drivers disagree on. Reylo types each value as your driver returns it by default; if you set the driver to decode a type another way, set the matching key:

```yaml title=".reylo.yaml"
types:
  dates: string
  bigint: bigint
```

| Key | Values | Default | Applies to |
| --- | --- | --- | --- |
| `dates` | `Date`, `string`, `temporal` | `Date` | `timestamptz`, `timestamp`, `date`; MySQL `DATETIME`, `TIMESTAMP`, `DATE` |
| `bigint` | `string`, `number`, `bigint` | `string` on Postgres, `number` on MySQL and SQLite | `bigint`; MySQL `BIGINT`; SQLite `INTEGER` |
| `decimal` | `string`, `number` | `string` | `numeric`; MySQL `DECIMAL` |
| `json` | `parsed`, `string` | `parsed` | `json`, `jsonb` and JSON the statement builds; MySQL `JSON` |
| `binary` | `Uint8Array`, `Buffer`, `ArrayBuffer`, `number[]` | `Uint8Array` | `bytea`; MySQL `BINARY`, `BLOB`; SQLite `BLOB` |

<Details summary="The driver options behind each setting">

- `dates: string`: `pg` with a timestamp `types.setTypeParser`, postgres.js with its `types` option, mysql2 and mariadb with `dateStrings: true`
- `bigint: bigint`: `pg` with a BigInt parser for `int8`, postgres.js with `postgres.BigInt`, Bun.sql with `bigint: true`, better-sqlite3 with `defaultSafeIntegers(true)`, node:sqlite with `readBigInts`, bun:sqlite with `safeIntegers`, libSQL with `intMode: "bigint"`
- `bigint: string`: mysql2 with `supportBigNumbers` and `bigNumberStrings`, libSQL with `intMode: "string"`
- `bigint: number`: mariadb with `bigIntAsNumber`
- `decimal: number`: mysql2 with `decimalNumbers`, mariadb with `decimalAsNumber`
- `json: string`: mysql2 and mariadb with `jsonStrings`

</Details>

<Details summary="How Buffer, Temporal and nested JSON values are typed">

- A `Buffer` is typed `Uint8Array`, which it extends. `binary: Buffer` types it `Buffer`, in a project with `@types/node`.
- A binary parameter takes a `Uint8Array`, a `Buffer` or not, on every driver: mariadb, which writes any other value as JSON, gets it from Reylo as a `Buffer`.
- On Postgres, an array parameter takes a JavaScript array on every driver, for a SQL array (`any(:ids)`, `:tags::text[]`) and for JSON (`:data::jsonb`) alike: Reylo writes it in the form the driver binds right.
- A `timestamptz` parameter takes a `Date`, or a string that names its zone: `"2026-10-12T19:06:48Z"`, `"2026-10-12 19:06:48+09"`, `"2026-10-12 19:06:48 Asia/Tokyo"`. A `timestamp` or `date` parameter, and on MySQL a `DATETIME`, `TIMESTAMP` or `DATE` one, has no zone and takes the wall-clock text, `"2026-10-12 19:06:48"` or `"2026-10-12"`: drivers write a `Date`'s time in different zones, the app's, the server's or UTC, so Reylo refuses one before the statement runs. Format a `Date` the driver returned for such a column before passing it back.
- A parameter the statement reads as JSON (`:data::jsonb`, `cast(:data as json)`, a `json` column) takes any JSON value, and the database receives its JSON text on every driver: a string is a JSON string, so `'{"a":1}'` is stored as the string `"{\"a\":1}"`, not as an object. To pass JSON text you already hold, cast it from text: `:data::text::jsonb`.
- With `dates: temporal`, the driver builds `Temporal` values, typed by TypeScript's `esnext.temporal` lib.
- The settings do not reach inside nested JSON: there the database writes each value as JSON.

</Details>

Some drivers return other defaults, and Reylo types each value the way the driver your code runs with returns it. It finds that driver in `package.json`: one in `dependencies` before one in `devDependencies`, and in the same list, your driver before the `pg`, postgres.js or mysql2 the type check needs:

<DialectTabs>
<Dialect value="Postgres">

PGlite returns `bigint` as a `number`, or as a `bigint` above 2^53, and Reylo types it so. The type check needs `pg` or postgres.js as well, and PGlite beside it in `dependencies` is the driver Reylo follows; PGlite kept in `devDependencies` for tests leaves an app on `pg` typed as `pg` returns.

On `pg`, pg-promise, Neon's Pool and Client, and PGlite, Reylo decodes the types those drivers leave as text or objects (enum and other arrays, `interval`, `numeric[]`), so the rows match the [Data types](#data-types) tables; it does so for its own queries only, and a parser you registered still wins. Reylo does not follow two drivers yet: Neon's `neon()` returns enum arrays as text, `interval` as an object and `numeric[]` as numbers, and Bun.sql returns enum, `uuid`, `citext` and range arrays as text.

</Dialect>
<Dialect value="MySQL">

mariadb returns `BIGINT` as a `bigint`, and PlanetScale returns dates and `BIGINT` as strings, and Reylo types them so. The type check needs `mysql2` too, and mariadb or PlanetScale beside it is the driver Reylo follows. Reylo does not follow two mariadb values yet: it returns `SET` as an array and `BIT(1)` as a boolean.

</Dialect>
<Dialect value="SQLite">

libSQL returns `BLOB` as an `ArrayBuffer`, and Cloudflare D1 as a `number[]`. Reylo follows each, found as `@libsql/client` and as `wrangler` (D1's). With two drivers in the same list, it takes the first of better-sqlite3, libSQL, `sqlite3`, `sqlite` and `wrangler`.

</Dialect>
</DialectTabs>

### `cli`

The `.sql` files `reylo generate` analyzes, as globs relative to `.reylo.yaml`: `include` replaces the default, every `.sql` file, and `exclude` adds to what is always left out: `node_modules`, build output, directories whose names start with a dot, and what git ignores. The type check reads the files `tsconfig.json` includes instead. See [In CI](#in-ci) for `reylo generate`.

```yaml title=".reylo.yaml"
cli:
  include: ["src/**/*.sql"]
  exclude: ["src/legacy/**"]
```

## Basic usage

Write the statement in a `.sql` file. `:id` is a parameter.

```sql title="get_user.sql" tab="Postgres" tab-group="dialect"
select id, name, email from users where id = :id
```

```sql title="get_user.sql" tab="MySQL" tab-group="dialect"
select id, name, email from users where id = :id
```

```sql title="get_user.sql" tab="SQLite" tab-group="dialect"
select id, name, email from users where id = :id
```

Import it, and run it with a client from your driver:

<DialectTabs follow>
<Dialect value="Postgres">

```ts twoslash title="main.ts"
import postgres from "postgres";
import getUser from "./get_user.sql";

const db = postgres(process.env.DATABASE_URL!);

const user = await getUser.run(db, { id: 1 });
//    ^?
await db.end(); // the client keeps the process alive until it ends
```

</Dialect>
<Dialect value="MySQL">

```ts twoslash title="main.ts"
import mysql from "mysql2/promise";
import getUser from "./get_user.sql";

const db = mysql.createPool(process.env.DATABASE_URL!);

const user = await getUser.run(db, { id: 1 });
//    ^?
await db.end(); // the pool keeps the process alive until it ends
```

</Dialect>
<Dialect value="SQLite">

```ts twoslash title="main.ts"
import Database from "better-sqlite3";
import getUser from "./get_user.sql";

const db = new Database("app.db");

const user = await getUser.run(db, { id: 1 });
//    ^?
db.close();
```

</Dialect>
</DialectTabs>

A query also has these members:

```ts twoslash title="main.ts"
import getUser, { type Params, type Row } from "./get_user.sql";
//                                  ^?

// the parameters as an array, in the order of getUser.params
await getUser.run(db, [1]);

// the statement bound to a client once, such as a transaction
const get = getUser.with(db);
await get({ id: 1 });

getUser.sql;          // the statement as written
getUser.params;       // ["id"]
getUser.cardinality;  // "maybeOne"
```

### What `run` resolves to

Reylo works out how many rows a statement can return, and `run` resolves to match:

| The statement | Row count | `run` resolves to |
| --- | --- | --- |
| A match on a primary or unique key, or `limit 1` | `maybeOne` | `Row \| null` |
| An aggregate without `group by`, a one-row `insert … returning` | `one` | `Row` |
| An `insert`, `update` or `delete` without `returning` | `none` | `void` |
| Anything else | `many` | `Row[]` |

<DialectTabs>
<Dialect value="Postgres">

A key match also counts through a join on the joined table's key, a unique index on an expression or with a `where`, and a `distinct` or `group by` over values the `where` pins.

</Dialect>
<Dialect value="MySQL">

Only a match on one table's own primary or unique key counts, with or without a `distinct` or `group by`: a joined table's key, a unique index on an expression, and a `distinct` or `group by` over pinned values that are not a key give `many`.

</Dialect>
<Dialect value="SQLite">

A key match also counts through a join on the joined table's key, and a `distinct` or `group by` over values the `where` pins. A unique index on an expression or with a `where` gives `many`.

</Dialect>
</DialectTabs>

At run time, a `one` query throws unless it gets exactly one row, and a `maybeOne` query throws when it gets more than one. No directive overrides the count.

### One statement per file

A `.sql` file holds one `select`, `insert`, `update`, `delete` or `values`; `merge` on Postgres; `replace` on MySQL and SQLite; or `table` on Postgres and MySQL. The type check reports every other `.sql` file it reads, imported or not, such as a migration or a schema. Keep those out of `tsconfig.json`:

```jsonc title="tsconfig.json"
{
  "compilerOptions": { /* ... */ },
```

## Examples

Each example shows the statement in Postgres, MySQL and SQLite, against [the schema at the top of the page](#schema); pick a dialect once and every example follows it. The examples call the client `db`.

### Get a row

A match on a primary or unique key is at most one row, so `run` resolves to the row or `null`.

```sql title="find_user.sql" tab="Postgres" tab-group="dialect"
select id, name from users where email = :email
```

```sql title="find_user.sql" tab="MySQL" tab-group="dialect"
select id, name from users where email = :email
```

```sql title="find_user.sql" tab="SQLite" tab-group="dialect"
select id, name from users where email = :email
```

```ts twoslash title="main.ts"
import findUser from "./find_user.sql";

const user = await findUser.run(db, { email: "ada@example.com" });
//    ^?
```

Reylo types each parameter from where the statement uses it: the column it is compared with or written to, the function it is passed to, or a cast. A cast is `::` in every dialect: MySQL and SQLite have no `::`, so Reylo writes their own `cast(… as …)`.

<Details summary="When nothing in the statement types a parameter" id="a-parameter-nothing-types">

<DialectTabs>
<Dialect value="Postgres">

Postgres types each parameter from its context. A bare `select :x` is `text`, a `string`, and `select :x is null` is an error (42P18) until a cast types it.

</Dialect>
<Dialect value="MySQL">

MySQL types every parameter: one that nothing else types, such as a bare `select :x`, is a `string`.

</Dialect>
<Dialect value="SQLite">

A parameter that nothing types is `unknown`: a bare `select :x`, or an argument of a function your application registers or of a table-valued function other than `json_each` and `json_tree`. A cast types it, and [`strict: true`](#strict) in `.reylo.yaml` makes an untyped parameter an error:

```sql
select length(:text::text) as n
```

</Dialect>
</DialectTabs>

</Details>
<Details summary="Using `$1` or `?` instead of `:name`" id="positional-parameters">

A statement can use its database's own positional form instead of `:name`. The key is then the number.

```sql title="user_by_id.sql" tab="Postgres" tab-group="dialect"
select id, name from users where id = $1
```

```sql title="user_by_id.sql" tab="MySQL" tab-group="dialect"
select id, name from users where id = ?
```

```sql title="user_by_id.sql" tab="SQLite" tab-group="dialect"
select id, name from users where id = ?1
```

```ts twoslash title="main.ts"
import userById from "./user_by_id.sql";

const user = await userById.run(db, { 1: 42 });
```

Mixing the two styles in one statement is an error.

</Details>

### Keep a list's order

Number the list's elements, and sort by the number.

```sql title="users_in_order.sql" tab="Postgres" tab-group="dialect"
-- with ordinality numbers the elements
select u.id, u.name
from unnest(:ids::int[]) with ordinality as i(id, position)
join users u on u.id = i.id
order by i.position
```

```sql title="users_in_order.sql" tab="MySQL" tab-group="dialect"
-- a for ordinality column numbers the elements
with input as (
  select :ids::json('{ "type": "array", "items": { "type": "int" } }') as ids
)
select u.id, u.name
from input, json_table(input.ids, '$[*]' columns (
  position for ordinality,
  id int path '$'
)) as i
join users u on u.id = i.id
order by i.position
```

```sql title="users_in_order.sql" tab="SQLite" tab-group="dialect"
-- json_each numbers the elements as key
with input as (
  select :ids::json('{ "type": "array", "items": { "type": "integer" } }') as ids
)
select u.id, u.name
from input, json_each(input.ids) as i
join users u on u.id = i.value
order by i.key
```

### Nest related rows

```sql title="user_with_posts.sql" tab="Postgres" tab-group="dialect"
    select jsonb_agg(jsonb_build_object(

      'title', p.title,
```

<Details summary="How the schema in a JSON parameter works" id="json-parameters">

A JSON parameter carries a schema in its cast. The schema gives the parameter its TypeScript type, and Reylo checks each value against it before the statement runs. The database never sees the schema: it receives the value as JSON text.

- The schema is JSON Schema, with one difference: `type` is `"object"`, `"array"`, or one of the dialect's types (below), as in `{ "type": "text" }`.
- A key is optional unless `required` lists it. A value that may be `null` says so in its type, `{ "type": ["text", "null"] }`, so `email` above is `email?: string | null`.
- A key the schema does not name is ignored, unless its object sets `"additionalProperties": false`.
- A nested object or array stays JSON: read it with the database's JSON functions, as in [Insert related rows](#insert-related-rows).
- A text type or `uuid` is a `string`, a number type a `number`, `boolean` a `boolean`, `json` and `jsonb` any JSON value.
- The checks are JSON Schema's validation keywords, such as `format`, `pattern`, `minLength`, `maxLength`, `minimum`, `maximum`, `multipleOf`, `enum`, `const`, `minItems`, `maxItems` and `uniqueItems`. `enum` and `const` also narrow the type. A value that fails makes `run` reject before the statement reaches the database, with every issue listed.
- `oneOf` makes a union of objects, told apart by a required `const` key, as in [Record events of several kinds](#record-events-of-several-kinds), and `allOf` combines objects. A union of plain values, such as `["text", "int"]`, is refused, since the statement reads a field into a column of one type.

<DialectTabs follow>
<Dialect value="Postgres">

The cast is `:users::jsonb('…')`, and Postgres receives `$1::jsonb`. A leaf type is a Postgres type, such as `"text"`, `"int"` or `"uuid"`.

</Dialect>
<Dialect value="MySQL">

The cast is `:users::json('…')`, and MySQL receives `cast(? as json)`. A leaf type is a MySQL type, such as `"varchar(255)"` or `"int"`.

</Dialect>
<Dialect value="SQLite">

The cast is `:users::json('…')`, and SQLite receives `?`. A leaf type is a type a `strict` table takes: `"text"`, `"integer"`, `"real"`, `"blob"` or `"any"`.

</Dialect>
</DialectTabs>

</Details>

### Insert related rows

Users with their posts, in one parameter. The posts find their user by `email`, a unique key.

<DialectTabs>
<Dialect value="Postgres">

Postgres writes both tables in one statement: a `with` inserts the users, and the statement inserts the posts.

```sql title="create_users_with_posts.sql"
with input as (
  select :users::jsonb('{
    "type": "array",
    "items": {
      "type": "object",
      "properties": {
        "name": { "type": "text" },
        "email": { "type": "text", "format": "email" },
        "posts": {
          "type": "array",
          "items": {
            "type": "object",
            "properties": { "title": { "type": "text" } },
            "required": ["title"]
          }
        }
      },
      "required": ["name", "email", "posts"]
    }
  }') as users
),
new_users as (
  insert into users (name, email)
  select u.name, u.email
  from input, jsonb_to_recordset(input.users) as u(name text, email text)
  returning id, email
)
insert into posts (user_id, title)
select n.id, p.title
from input
cross join jsonb_to_recordset(input.users) as u(email text, posts jsonb)
join new_users n on n.email = u.email
cross join jsonb_to_recordset(u.posts) as p(title text)
```

```ts twoslash title="main.ts"
import createUsersWithPosts, { type Params } from "./create_users_with_posts.sql";
//                                  ^?

await createUsersWithPosts.run(db, {
  users: [
    { name: "Ada", email: "ada@example.com", posts: [{ title: "Notes" }] },
  ],
});
```

</Dialect>
<Dialect value="MySQL">

MySQL cannot write inside a `with`, so the users and the posts are two statements, run in one transaction:

```sql title="insert_users.sql"
insert into users (name, email)
with input as (
  select :users::json('{
    "type": "array",
    "items": {
      "type": "object",
      "properties": {
        "name": { "type": "text" },
        "email": { "type": "varchar(255)", "format": "email" }
      },
      "required": ["name", "email"]
    }
  }') as users
)
select u.name, u.email
from input, json_table(input.users, '$[*]' columns (
  name text path '$.name',
  email varchar(255) path '$.email'
)) as u
```

```sql title="insert_posts.sql"
insert into posts (user_id, title)
with input as (
  select :users::json('{
    "type": "array",
    "items": {
      "type": "object",
      "properties": {
        "email": { "type": "varchar(255)" },
        "posts": {
          "type": "array",
          "items": {
            "type": "object",
            "properties": { "title": { "type": "text" } },
            "required": ["title"]
          }
        }
      },
      "required": ["email", "posts"]
    }
  }') as users
)
select users.id, u.title
from input, json_table(input.users, '$[*]' columns (
  -- the collation of users.email
  email varchar(255) collate utf8mb4_0900_ai_ci path '$.email',
  nested path '$.posts[*]' columns (title text path '$.title')
)) as u
join users on users.email = u.email
where u.title is not null
```

```ts twoslash title="main.ts"
import mysql from "mysql2/promise";
import insertUsers, { type Params } from "./insert_users.sql";
//                         ^?
import insertPosts from "./insert_posts.sql";

const db = mysql.createPool(process.env.DATABASE_URL!);
const users = [
  { name: "Ada", email: "ada@example.com", posts: [{ title: "Notes" }] },
];

const conn = await db.getConnection();
try {
  await conn.beginTransaction();
  await insertUsers.run(conn, { users });
  await insertPosts.run(conn, { users });
  await conn.commit();
} catch (error) {
  await conn.rollback();
  throw error;
} finally {
  conn.release();
}
```

A `JSON_TABLE` column takes the connection's collation, `utf8mb4_unicode_ci` under mysql2. Comparing it with a column of another collation is an error, so the `email` column names the collation of `users.email`.

</Dialect>


### Run statements in a transaction

A transaction, a savepoint or a connection taken from a client is a client too:

<DialectTabs>

## Type checking

### What an error looks like

An error in a `.sql` file is a type error at its line and column, in the type check and in the editor:

```ansi title="Terminal"
$ tsc --noEmit --runExternalCode
[96mget_user.sql[0m:[93m1[0m:[93m12[0m - [91merror[0m[90m reylo6: [0mcolumn "nmae" does not exist (42703)

[7m1[0m select id, nmae, email
[7m [0m [91m           ~~~~[0m

Found 1 error in get_user.sql[90m:1[0m
```

A wrong argument is an error at the call site:

```ts twoslash title="main.ts"
// @errors: 2322
import getUser from "./get_user.sql";

const user = await getUser.run(db, { id: "1" });
```

While any `.sql` file has an error, `tsc` reports no TypeScript error, so fix the SQL first. At run time, `run` rejects with the driver's own error, and with Reylo's when the rows do not fit the row count ([What `run` resolves to](#what-run-resolves-to)).

### When the schema changes

Reylo runs no migrations: keep your own tool. After a migration, the next type check sees the new schema. A statement that names a dropped or renamed column fails in its `.sql` file, and a call site that reads a column the statement no longer returns fails in TypeScript.

Reylo keys each answer in `.reylo/` by a fingerprint of the schema, so it asks the database again only for a schema it has not seen. A long-running process, such as an editor or a dev server, trusts a fingerprint for 5 seconds before it checks the schema again.

### In CI

A CI job that type-checks starts the database, applies the migrations, and runs `tsc --noEmit --runExternalCode` with `DATABASE_URL` set. Tests need the database too, or a filled `.reylo/`: Vitest's [Vite plugin](#setup-vite) and Jest's [transformer](#setup-jest) analyze each `.sql` file as a build does.

Every step that loads a `.sql` file (the type check, a plugin, the preload) keeps its analysis in `.reylo/`, and a later step reads it from there:

- `.reylo/` is a cache with its own `.gitignore`; git skips it.
- When the database answers, an entry made against another schema is analyzed again.
- When it cannot be reached, the entries are used as they are.
- With no database, a statement that `.reylo/` lacks is an error.

So where the build cannot reach the database, such as a container build, run `reylo generate` where it can, and carry `.reylo/` to the build:

```text
$ reylo generate
postgres at localhost/reylo_docs (DATABASE_URL in .env)
  src/admin/find_by_email.sql  ✗
  src/admin/set_email.sql      ✓
  src/queries/count_users.sql  ✓
  src/queries/create_user.sql  ✓
  src/queries/get_user.sql     ✓
  src/queries/list_users.sql   ✓

src/admin/find_by_email.sql:1:12: column "nmae" does not exist (42703)
  1 | select id, nmae
    |            ^^^^

Skipped 1 file that is not one query (a migration?): db/schema.sql

✗ 1 of 6 queries failed (0.1 s)
```

`reylo generate` reads every `.sql` file under the given paths, the current directory by default. It skips `node_modules`, build output, dot directories and what git ignores; the [`cli`](#cli) keys of `.reylo.yaml` change the set. `--force` asks the database again for every statement. The exit code is 1 when a query fails.

Reylo keys each entry by the server it came from (scheme, user, host, port and database), or by the SQLite file's absolute path. So the build sets the same URL as the place where `reylo generate` ran (`DATABASE_URL`, or [`direct_url`](#direct_url) when it is set), even though it cannot connect, and a SQLite project keeps its path.

## Dialects

Postgres is the reference dialect. MySQL and SQLite type less, and each lists its limits.

### Postgres

Reylo prepares the statement on the server and reads the description of its parameters and columns. It then reads the catalog for `NOT NULL`, keys and enum labels.

| What | Where it comes from |
| --- | --- |
| Parameter types | the server's description of the prepared statement |
| Column types | the server's description; an enum as its labels, a domain as its base type |
| Nullability | `NOT NULL` in the catalog, outer joins, the expressions |
| Row count | primary and unique keys, aggregates, `limit 1`, `returning` |
| Nested JSON | `jsonb_build_object`, `jsonb_agg`, and `to_jsonb` of a row, typed from their arguments |

A function's body is opaque: a call has the function's declared type.

### MySQL

Reylo prepares the statement on the server, which reports the column types, `NOT NULL`, and a type for each parameter from its context. Reylo adds which parameters may be null, the row count and the shape of JSON built in the statement.

| What | Where it comes from |
| --- | --- |
| Parameter types | the prepared statement's metadata; whether one may be null, from the statement, as on Postgres |
| Column types | the prepared statement's metadata |
| Nullability | the server's `NOT NULL` flag |
| Row count | primary and unique keys, aggregates; a write is `void` |
| Nested JSON | `json_object` and `json_arrayagg`, typed from their arguments |

MySQL's limits:

- MySQL has no `returning`: a write resolves to `void`. Read a new id with `select last_insert_id()`, as in [Insert a row](#insert-a-row).
- Nullability is the server's flag: sound for `NOT NULL`, cautious for string and date functions.
- A prepare error has no position, so the error covers the whole statement.
- Reylo is tested against MySQL 8.0, 8.4, 9.7 and 26.7, not MariaDB. Typing a parameter from its context needs MySQL 8.0.22 or later.

### SQLite

Reylo reads the schema from the database file and prepares the statement against its own copy of SQLite. SQLite then reports where every column and parameter comes from.

| What | Where it comes from |
| --- | --- |
| Parameter types | where SQLite places the parameter: a comparison with a column, an element of a row value, an `insert` or `update` column, a `cast`, `limit` and `offset` |
| Column types | the declared type's affinity |
| Nullability | `NOT NULL` in the table, outer joins, Reylo's table of SQLite's built-in functions |
| Row count | unique indexes and `integer primary key` |
| Nested JSON | `string` |

SQLite's limits:

- A declared type is an affinity, not a constraint: a column in a table without `strict` can hold a value of another type.
- SQLite has no date, time or boolean type. A date in a `text` column is a `string`; a column declared `boolean`, `date` or `datetime` is `number | string`.
- The result of a function the application registers, or of `json_extract`, `->` and `->>`, is `unknown`.
- JSON built in the statement is a `string`: the driver returns the text.
