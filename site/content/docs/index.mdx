```sql title="get_user.sql"
select id, name, email, role, tags, created_at, id + 1 as next_id
from users
where id = :id and name = :name
```

```ts title="main.ts"
import postgres from "postgres";
import getUser from "./get_user.sql";

const sql = postgres(process.env.DATABASE_URL!);

const user = await getUser.run(sql, { id: 1, name: "ada" });
// user: {
//   id: number;
//   name: string;
//   email: string | null;
//   role: "admin" | "member";
//   tags: string[];
//   created_at: Date;
//   next_id: number;
// } | null
```

Every type above comes from the database.

```sql title="schema.sql"
);

create table posts (
  id serial primary key,
  user_id integer not null references users (id),
  title text not null,
  body text,
  published_at timestamptz
);
```

## How it works

Porg is a [content mapper](https://github.com/microsoft/typescript-go/pull/4712), a feature new in TypeScript 7.1. A content mapper is a package that turns a file type TypeScript does not know into a typed module, in the type checker and in the editor.

Bundlers have loaded `.sql` and other files as modules for years, but the type checker could not see inside them. Content mappers are the missing half: a loader is now type safe from end to end.

To type a query, Porg sends it to your running database, which prepares it without running it. The database reports what the query takes and what it returns:

- the parameter types
- the column types
- nullability, from `NOT NULL` and outer joins
- the row count, from primary and unique keys

Porg connects through the driver your project already uses: `pg`, `postgres` or `mysql2`, or `node:sqlite` for SQLite. It keeps each answer in `.porg/` and asks again when the schema changes.

## Setup

Install Porg and point it at your database, then add it to each tool that loads your code.

### Install

```npm
npm install porg
npm install -D typescript@next
```

Content mappers are in the TypeScript 7.1 dev builds (`typescript@next`). Porg needs Node 24 or later.

Porg reads `DATABASE_URL` from the environment, or from `.env.local` or `.env` next to `package.json`:

```sh title=".env"
DATABASE_URL=postgres://localhost:5432/app   # mysql://… for MySQL, file:./app.db for SQLite
```

Other settings go in a `.porg.yaml` file: see [The project file](/details#the-project-file).

### TypeScript

Add Porg to `tsconfig.json`:

```jsonc title="tsconfig.json"
{
  "compilerOptions": {
    // ...
  },
  "contentMappers": [{ "package": "porg", "extensions": [".sql"] }]
}
```

Type-check with `--runExternalCode`. Without the flag, `tsc` ignores content mappers.

```json title="package.json"
{
  "scripts": {
    "typecheck": "tsc --noEmit --runExternalCode"
  }
}
```

### Runtimes

A preload turns each `.sql` import into a module as it loads.

```sh tab="Node"
node --import porg/register main.ts

# or for every node process
export NODE_OPTIONS="--import porg/register"
```

```sh tab="Bun"
bun --preload porg/register main.ts

# or for every bun command: preload = ["porg/register"] in bunfig.toml
```

```sh tab="nub"
nub --import porg/register main.ts
```

### Bundlers and frameworks

A bundler plugin turns each `.sql` import into a module at build time, so a bundled app needs no preload.

## Write queries

A `.sql` file holds one statement. Porg types its parameters, its columns, and how many rows it returns.

### Parameters

Write a parameter as `:name`, on every dialect.

```sql title="search.sql"
select id, name from users
where name like :pattern and role = :role
```

```ts
import search from "./search.sql";

await search.run(sql, { pattern: "a%", role: "admin" });
// params: { pattern: string; role: "admin" | "member" }
```

More on parameters, from positional forms to `null`: see [Parameters](/details#parameters).

### Columns and nullability

Column types and `NOT NULL` come from the schema. Outer joins and expressions decide the rest.

```sql title="user_posts.sql"
select u.name, p.title, coalesce(p.title, '') as label
from users u
left join posts p on p.user_id = u.id
```

```ts
const rows = await userPosts.run(sql);
// {
//   name: string;          not null in the table
//   title: string | null;  the outer side of a left join
//   label: string;         coalesce with a non-null default
// }[]
```

### Row count

The statement and the schema decide how many rows a query returns, and `run` resolves to the matching type.

```sql
-- get_user.sql
select * from users where id = :id

-- count_users.sql
select count(*) from users

-- list_users.sql
select * from users

-- delete_user.sql
delete from users where id = :id
```

```ts
await getUser.run(sql, { id: 1 });     // Row | null    a primary-key match, or limit 1
await countUsers.run(sql);             // Row           an aggregate without group by
await listUsers.run(sql);              // Row[]         anything else
await deleteUser.run(sql, { id: 1 });  // void          a write without returning
```

### Nested JSON

JSON built in the statement keeps its shape.

```sql title="user_with_posts.sql"
select u.id, u.name,
  coalesce((
    select jsonb_agg(jsonb_build_object('id', p.id, 'title', p.title, 'body', p.body, 'at', p.published_at))
    from posts p where p.user_id = u.id
  ), '[]') as posts
from users u
where u.id = :id
```

```ts
const user = await userWithPosts.run(sql, { id: 1 });
// {
//   id: number;
//   name: string;
//   posts: { id: number; title: string; body: string | null; at: string | null }[];
// } | null
```

Inside JSON, a timestamp is the string the database wrote.

### The module

A `.sql` import exports the query and its types.

```ts
import getUser from "./get_user.sql";                // the query
import type { Params, Row } from "./get_user.sql";   // its parameter and row types

getUser.sql;          // the statement as written
getUser.params;       // ["id", "name"]
getUser.cardinality;  // "maybeOne"
```

## Run queries

Pass `run` the client of your driver and the parameters. It returns a promise of the driver's rows.

```ts
const user = await getUser.run(sql, { id: 1, name: "ada" });
const users = await listUsers.run(sql); // no parameters, no second argument
```

The `with` method binds a client once:

```ts
const get = getUser.with(tx); // a transaction from your driver is a client too
await get({ id: 1, name: "ada" });
```

The synchronous SQLite drivers take `runSync`:

```ts
const user = getUser.runSync(db, { id: 1 }); // better-sqlite3, node:sqlite, bun:sqlite
```

Porg imports no driver. It works with the client of any of these:

- Postgres
  - `pg`
  - `postgres` (postgres.js)
  - `Bun.sql`
  - `@electric-sql/pglite`
  - `@neondatabase/serverless`
  - `pg-promise`
  - `@vercel/postgres`
- MySQL
  - `mysql2`
  - `mariadb`
  - `@planetscale/database` (1.x)
- SQLite
  - `better-sqlite3`
  - `node:sqlite`
  - `bun:sqlite`
  - `@libsql/client`
  - Cloudflare D1
  - `sqlite3`
  - `sqlite`

Drivers disagree on dates and 64-bit integers. On Postgres and MySQL, the `types` section of `.porg.yaml` says what your driver returns:

```yaml title=".porg.yaml"
types:
  dates: Date     # Date (the default), string or temporal
  bigint: string  # string (the Postgres default), number (the MySQL default) or bigint
```

Which driver option needs which setting: see [Dates and 64-bit integers](/details#dates-and-64-bit-integers).

## Dialects

Postgres is the reference dialect. MySQL and SQLite type less: see [Dialect limits](/details#dialect-limits).

### Postgres

Porg prepares the statement on the server and reads the description of its parameters and columns. It then reads the catalog for `NOT NULL`, keys and enum labels.

| What | Where it comes from |
| --- | --- |
| Parameter types | the server's description of the prepared statement |
| Column types | the server's description; an enum as its labels, a domain as its base type |
| Nullability | `NOT NULL` in the catalog, outer joins, the expressions |
| Row count | primary and unique keys, aggregates, `limit 1`, `returning` |
| Nested JSON | `jsonb_build_object`, `jsonb_agg` and `to_jsonb`, typed from their arguments |

### MySQL

Porg prepares the statement on the server, which reports the column types, `NOT NULL`, and a type for each parameter from its context. Porg adds the row count and the shape of JSON built in the statement.

| What | Where it comes from |
| --- | --- |
| Parameter types | the server's prepare |
| Column types | the server's prepare |
| Nullability | the server's `NOT NULL` flag |
| Row count | primary and unique keys, aggregates; a write is `void` (MySQL has no `returning`) |
| Nested JSON | `json_object` and `json_arrayagg`, typed from their arguments |

### SQLite

Porg reads the schema from the database file and prepares the statement against its own copy of SQLite. SQLite then reports where every column and parameter comes from.

| What | Where it comes from |
| --- | --- |
| Parameter types | where SQLite places the parameter: a comparison with a column, an `insert` or `update` column, a `cast`, `limit` and `offset` |
| Column types | the declared type's affinity |
| Nullability | `NOT NULL` in the table, outer joins, Porg's table of SQLite's built-in functions |
| Row count | unique indexes and `integer primary key` |
| Nested JSON | `string` |
