<p className="dk-subheader">Import `.sql` files into your TypeScript code with full type inference</p>

Reylo lets you import `.sql` files with full type safety. It's powered by TypeScript [content mappers](https://github.com/microsoft/typescript-go/pull/4712), introduced in TypeScript 7.1 (currently [in beta](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/)), an official mechanism for integrating external file types directly into TypeScript compilation.

```ts twoslash tab="main.ts" dialect="postgres"
// @hover: getAuthor author
import postgres from "postgres";
import getAuthor from "./get_author.sql";

const db = postgres(process.env.DATABASE_URL!);

// hover over author to see its type
const author = await getAuthor.run(db, { id: 1 });
```

```sql tab="get_author.sql"
select u.id, u.name, count(p.id)::int as post_count
from users u
left join posts p on p.user_id = u.id
where u.id = :id::int
group by u.id
```

<div className="dk-features">

- 💪 **The full power of SQL.** Any statement your database runs, in its own dialect.
- 🌵 **DRY.** The types come from the SQL itself: no hand-written row types, no schema file to keep in sync.
- 🎯 **Checked against your database.** A misspelled column, a wrong parameter or a dropped table is a type error, in `tsc` and in your editor.
- 🤖 **Agent-friendly.** Each fact lives in one place, so an agent cannot leave a stale type behind, and the type check finds every caller it missed.
- 🧩 **Postgres, MySQL and SQLite.** Bring your own driver: `pg`, postgres.js, `mysql2`, `better-sqlite3`, Bun, Cloudflare D1 and [more](#supported-drivers).
- ⚡ **No codegen.** The type checker asks Reylo directly: no generated files, no watcher.

### Install

Reylo needs:

- **TypeScript 7.1 (currently in beta).** The first release with content mappers.
- **Node 24 or later.**
- **A running dev database.** Postgres, MySQL 8.0.22 or later, or a SQLite file: Reylo reads your current schema from it. See [`.reylo.yaml`](#reyloyaml) to point Reylo at it.

```sh
npm install reylo
npm install -D @reylosql/postgres  # or mysql, sqlite
npm install -D typescript@beta
```

### `.reylo.yaml`

Reylo finds your dev database through the `DATABASE_URL` environment variable.

To override this, create a `.reylo.yaml` file in your project root and set the `url` field:

```yaml title=".reylo.yaml"
url: postgres://localhost:5432/app
```

You can also reference other environment variables via string interpolation:

```yaml title=".reylo.yaml"
url: ${APP_DATABASE_URL}
```

Or specify a set of `.env` files to load:

```yaml title=".reylo.yaml"
# the default is [.env.local, .env]
env: [.env.development, .env]
```

### TypeScript

Add Reylo to `tsconfig.json`:

```jsonc title="tsconfig.json"
{
  "compilerOptions": { /* ... */ },
  "contentMappers": [ // [!code ++]
    { "package": "reylo", "extensions": [".sql"] } // [!code ++]
  ] // [!code ++]
}
```

Then type-check with `--runExternalCode`, which lets `tsc` run content mappers:

```jsonc title="package.json"
{
  "scripts": {
    "typecheck": "tsc --noEmit --runExternalCode" // [!code ++]
  }
}
```

## Usage

Write a query in a `.sql` file, import it, and run it with your database driver. Reylo uses your live dev database to compile the query and retrieve its types.

```ts twoslash tab="main.ts" dialect="postgres"
import postgres from "postgres";
import getUser from "./get_user.sql";

const db = postgres(process.env.DATABASE_URL!);
const user = await getUser.run(db, { id: 1 });
```

```sql tab="get_user.sql" dialect="all"
select id, name, email from users where id = :id::int
```

### `.sql`

The compiled query, as Reylo sends it to your database:

```ts twoslash
import getUser from "./get_user.sql";

getUser.sql;
//      ^?
```

### `.raw`

The file's contents, before Reylo compiles its [parameters](#parameters):

```ts twoslash
import getUser from "./get_user.sql";

getUser.raw;
//      ^?
```

### `.run()`

Runs the query with your driver's client:

```ts twoslash
import getUser from "./get_user.sql";

const user = await getUser.run(db, { id: 1 });
//    ^?
```

It resolves to the rows, shaped by how many the query can return:

| The query | Resolves to |
| --- | --- |
| A match on a primary or unique key, or `limit 1` | `Row \| null` |
| An aggregate without `group by`, a one-row `insert … returning` | `Row` |
| An `insert`, `update` or `delete` without `returning` | `void` |
| Anything else | `Row[]` |

It throws when the rows don't fit the shape, such as a second row for `Row | null`. The client can also be a transaction or a connection ([Supported drivers](#supported-drivers)).

### `.runSync()`

Runs the query synchronously, on `better-sqlite3`, `node:sqlite`, `bun:sqlite` and the `Database` of `@tursodatabase/database/compat`:

```ts twoslash dialect="sqlite"
import Database from "better-sqlite3";
import getUser from "./get_user.sql";

const db = new Database("app.db");
const user = getUser.runSync(db, { id: 1 });
//    ^?
```

### `.with()`

Binds the query to a client, and returns a function that takes the parameters:

```ts twoslash
import getUser from "./get_user.sql";

const get = getUser.with(db);
const user = await get({ id: 1 });
```

## Parameters

Reylo's own syntax works the same on Postgres, MySQL and SQLite, and Reylo compiles it for your database.

### Named parameters

Name a parameter with a colon, and cast it with `::`:

```sql tab="find_posts.sql" dialect="all"
select id, title from posts
where user_id = :user_id::int
  and title like :pattern::text
order by id
limit :limit::int
```

```ts twoslash tab="main.ts"
import findPosts from "./find_posts.sql";

const posts = await findPosts.run(db, {
  user_id: 1,
  pattern: "%SQL%",
  limit: 10,
});
```

### Casts

Give each parameter its type with `::type`, on any database. Reylo compiles it to MySQL's and SQLite's own `cast`, and checks each value when you call `.run()`:

```ts twoslash
import findPosts from "./find_posts.sql";

findPosts.sql;
//        ^?
```

### JSON parameters

When casting to `json` or `jsonb`, you can define a JSON Schema annotation:

```sql tab="record_signup.sql" dialect="all"
insert into events (kind, payload)
values ('signup', :payload::json('{
  "type": "object",
  "properties": {
    "plan": { "type": "string", "enum": ["free", "pro"] },
    "referrer": { "type": "string" }
  },
  "required": ["plan"]
}'))
```

```ts twoslash tab="main.ts"
import recordSignup from "./record_signup.sql";

await recordSignup.run(db, { payload: { plan: "pro" } });
//                           ^?
```

Reylo uses it to infer the parameter's type, and validates your input against the schema when you call `.run()`.

The examples use JSON parameters to [insert many rows](#insert-many-rows), [insert related rows](#insert-related-rows) and [record events of several kinds](#record-events-of-several-kinds).

## Configuration

Reylo reads its settings from `.reylo.yaml`, beside `package.json`. Every key is optional:

```yaml title=".reylo.yaml"
# the dev database Reylo reads your schema from (the default)
url: ${DATABASE_URL}
# a direct connection for Reylo's analysis, past a pooler
direct_url: ${DIRECT_URL}
# the .env files Reylo reads (the default)
env: [.env.local, .env]
# make a parameter whose type cannot be inferred an error
strict_params: true
```

### `url`

The dev database Reylo reads your schema from. The scheme names the dialect:

```sh title=".env" tab="Postgres" tab-group="dialect"
# or postgresql://; the type check uses your pg or postgres.js
DATABASE_URL=postgres://localhost:5432/app
```

```sh title=".env" tab="MySQL" tab-group="dialect"
# or mariadb://; the type check uses your mysql2
DATABASE_URL=mysql://root@localhost:3306/app
```

```sh title=".env" tab="SQLite" tab-group="dialect"
# or sqlite:; the path starts at package.json; no driver needed
DATABASE_URL=file:./app.db
```

A `${VAR}` comes from the environment, then from the [`env`](#env) files:

```yaml title=".reylo.yaml"
# the default is ${DATABASE_URL}
url: ${APP_DATABASE_URL}
```

### `direct_url`

A direct connection for Reylo's analysis, past a pooler: describing a query through a pooler in transaction mode, such as PgBouncer's, can fail. Your app's client is not affected.

```yaml title=".reylo.yaml"
url: ${DATABASE_URL}
# no default
direct_url: ${DIRECT_URL}
```

### `env`

The `.env` files Reylo reads, relative to `.reylo.yaml`. The first file that sets a variable wins, and the environment wins over every file.

```yaml title=".reylo.yaml"
# the default is [.env.local, .env]
env: [.env.development, .env]
```

### `strict_params`

With `strict_params: true`, a [parameter whose type cannot be inferred](#a-parameter-nothing-types) is an error that says to [cast it](#casts), instead of `unknown`.

```yaml title=".reylo.yaml"
# the default is false
strict_params: true
```

## How it works

Reylo is a [content mapper](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/#content-mappers), the kind of plugin [TypeScript 7.1](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/) introduced for files that aren't TypeScript.

Whenever the type checker meets a `.sql` import, in `tsc` or in your editor, it hands Reylo the file and takes back the module's types.

<HowItWorksDiagram />

To type a query, Reylo has your live database prepare it, without running it, and reads the catalog. From the answer, it learns:

- the parameter types
- the column types
- nullability, from `NOT NULL` and outer joins
- the row count, from keys, aggregates, `limit 1` and `returning`

At run time, the [preload](#node) or a bundler [plugin](#plugins) turns the same file into a module that runs the query through your driver.

Reylo caches each answer in `.reylo/`, keyed by a fingerprint of the schema.

After a migration, the next type check sees the new schema: a dropped column fails in the `.sql` file that names it, and in the code that reads it.

<Details summary="What an error looks like" id="errors">

An error in a `.sql` file is a type error at its line and column, in the type check and in the editor:

```ansi title="Terminal"
$ tsc --noEmit --runExternalCode
[96mget_user.sql[0m:[93m1[0m:[93m12[0m - [91merror[0m[90m reylo6: [0mcolumn "nmae" does not exist (42703)

[7m1[0m select id, nmae, email
[7m [0m [91m           ~~~~[0m

Found 1 error in get_user.sql[90m:1[0m
```

A wrong argument is an error at the call site:

```ts twoslash
// @errors: 2322
import getUser from "./get_user.sql";

const user = await getUser.run(db, { id: "1" });
```

While a `.sql` file has an error, `tsc` holds back the TypeScript errors, so fix the SQL first.

<Dialect value="MySQL">

A MySQL prepare error has no position, so the error covers the whole statement.

</Dialect>
</DialectTabs>

</Details>

<Details summary="Where each type comes from, in each dialect" id="sources">

<DialectTabs>
<Dialect value="Postgres">

Reylo sends the query to the live database [prepared](https://www.postgresql.org/docs/current/sql-prepare.html) and reads back the database's own type information on its parameters and return type. This information is cross-referenced against the schema catalog, enabling high-fidelity type inference for any query.

| What | Where it comes from |
| --- | --- |
| Parameter types | the server's description of the prepared statement |
| Column types | the server's description; an enum as its labels, a domain as its base type, a JSON column as what its JSON Schema `CHECK` admits |
| Nullability | the catalog's `NOT NULL`, outer joins, the expressions |
| Row count | primary and unique keys, aggregates, `limit 1`, `returning` |
| Nested JSON | built with `jsonb_build_object`, `jsonb_agg` or `to_jsonb` of a row, typed from their arguments |

</Dialect>
<Dialect value="MySQL">

Reylo sends the query to the live database [prepared](https://dev.mysql.com/doc/refman/8.4/en/sql-prepared-statements.html) and reads back the database's own type information on its parameters and return type.

Reylo adds which parameters may be null, the row count, and the shape of JSON the query builds.

| What | Where it comes from |
| --- | --- |
| Parameter types | the prepared statement's metadata; whether one may be null, from the statement, as on Postgres |
| Column types | the prepared statement's metadata; a JSON column read from its table as what its JSON Schema `CHECK` admits |
| Nullability | the server's `NOT NULL` flag |
| Row count | primary and unique keys, aggregates; a write is `void` |
| Nested JSON | built with `json_object` and `json_arrayagg`, typed from their arguments |

</Dialect>
<Dialect value="SQLite">

Reylo reads the schema from the database file and [prepares](https://sqlite.org/c3ref/prepare.html) the query in its own copy of SQLite, which reports where each column and parameter comes from.

| What | Where it comes from |
| --- | --- |
| Parameter types | where SQLite places the parameter: a comparison with a column, an element of a row value, an `insert` or `update` column, a `cast`, `limit` and `offset` |
| Column types | the declared type's affinity |
| Nullability | the table's `NOT NULL`, outer joins, Reylo's table of SQLite's built-in functions |
| Row count | unique indexes and `integer primary key` |
| Nested JSON | `string` |

</Dialect>
</DialectTabs>

</Details>

<Details summary="When a parameter's type cannot be inferred" id="a-parameter-nothing-types">

It's `unknown` until a [cast](#casts) types it, and an error with [`strict_params: true`](#strict_params).

<DialectTabs>
<Dialect value="Postgres">

Postgres types a parameter from its context: a bare `select :x` is a `string`, and `select :x is null` is an error until a cast types it.

</Dialect>
<Dialect value="MySQL">

MySQL types every parameter: one that nothing else types, such as a bare `select :x`, is a `string`.

</Dialect>
<Dialect value="SQLite">

A bare `select :x`, or an argument of a function your application registers or of a table-valued function other than `json_each` and `json_tree`, has no type until a cast gives it one:

```sql
select length(:text::text) as n
```

</Dialect>
</DialectTabs>

</Details>

<Details summary="Which matches count as a key, in each dialect" id="key-matches">

<DialectTabs>
<Dialect value="Postgres">

Also a key match:

- a join on the joined table's key
- a unique index on an expression or with a `where`
- a `distinct` or `group by` over values the `where` pins

</Dialect>
<Dialect value="MySQL">

Only a match on one table's own primary or unique key counts, with or without a `distinct` or `group by`. These give `many`:

- a joined table's key
- a unique index on an expression
- a `distinct` or `group by` over pinned values that are not a key

</Dialect>
<Dialect value="SQLite">

Also a key match:

- a join on the joined table's key
- a `distinct` or `group by` over values the `where` pins

A unique index on an expression or with a `where` gives `many`.

</Dialect>
</DialectTabs>

</Details>

<Details summary="In CI, and in builds without a database" id="in-ci">

A CI job that type-checks starts the database, applies the migrations, and runs `tsc --noEmit --runExternalCode` with `DATABASE_URL` set. Tests need the database too, or a filled `.reylo/`.

Every step that loads a `.sql` file (the type check, a plugin, the preload) keeps its analysis in `.reylo/`, and a later step reads it from there:

- The `.reylo/` directory is a cache with its own `.gitignore`, so git skips it.
- When the database answers, an entry made against another schema is analyzed again. An editor or a dev server checks the schema again at most every 5 seconds.
- When the database is out of reach, the entries are used as they are, and a statement that `.reylo/` lacks is an error.

A build that can't reach the database, such as a container build, uses the `.reylo/` a type check filled. Its entries are keyed by the database's URL, so the build sets the same URL, even though it can't connect.

</Details>

## Supported drivers

The type check reads your schema through `pg` or postgres.js on Postgres, and `mysql2` on MySQL. An app on another driver adds one as a dev dependency.

## Data types

Reylo decodes its own queries' values itself, so every driver gives the same types. A 64-bit integer is a `bigint`, a decimal its exact text, and an instant its ISO 8601 text in UTC: no value is a `Date`.

<Dialect value="Postgres">

| SQL type | TypeScript |
| --- | --- |
| `smallint`, `integer`, `oid` | `number` |
| `bigint` | `bigint` |
| `real`, `double precision` | `number` |
| `numeric`, `money` | `string` |
| `text`, `varchar`, `char` | `string` |
| `boolean` | `boolean` |
| `uuid` | `string` |
| `date` | `string`, as `2026-10-20` |
| `timestamp` | `string`, as `2026-10-20T10:00:00.123456` |

| `time`, `timetz`, `interval` | `string` |
| `json`, `jsonb` | `unknown` |

| `jsonb_build_object(…)`, `jsonb_agg(…)` | the object or array it builds |
| `bytea` | `Uint8Array` |

## Examples

Each example runs against [the schema at the top of the page](#schema), and calls the client `db`. Pick a dialect once, and every example follows it.

### List rows

A query that can match more than one row resolves to an array.

```sql tab="list_users.sql" dialect="all"
select id, name, role, tags, created_at from users
order by created_at desc
limit :limit::int
```

```ts twoslash tab="main.ts"
import listUsers from "./list_users.sql";

const users = await listUsers.run(db, { limit: 20 });
//    ^?
```

### Count rows

An aggregate without `group by` is exactly one row.

```sql tab="count_posts.sql" dialect="all"
select count(*) as total from posts where user_id = :user_id::int
```

```ts twoslash tab="main.ts"
import countPosts from "./count_posts.sql";

const { total } = await countPosts.run(db, { user_id: 1 });
//      ^?
```

### Filter on an optional value

A `coalesce` lets a parameter be `null`: here `null` matches every user. A parameter takes `null` only where the query allows it, such as a `coalesce` or a nullable column it is written to.

```sql tab="posts_by_user.sql" dialect="all"
select id, title from posts
where user_id = coalesce(:user_id::int, user_id)
```

```ts twoslash tab="main.ts"
import postsByUser from "./posts_by_user.sql";

const posts = await postsByUser.run(db, { user_id: null });
//                                        ^?
```

### Sort by a chosen column

A parameter is a value, never a column name, so choose the column with `case`:

```sql tab="sorted_users.sql" dialect="all"
select id, name, created_at from users
order by
  case :sort::text when 'name' then name end,
  created_at desc
```

```ts twoslash tab="main.ts"
import sortedUsers from "./sorted_users.sql";

const users = await sortedUsers.run(db, { sort: "name" });
//    ^?
```

### Search several columns

Each parameter appears once in a query. To use a value twice, select it once in a `with`:

```sql tab="search_users.sql" dialect="all"
with input as (
  select concat('%', :q::text, '%') as pattern
)
select id, name from users, input
where name like input.pattern or email like input.pattern
```

```ts twoslash tab="main.ts"
import searchUsers from "./search_users.sql";

const users = await searchUsers.run(db, { q: "ada" });
//    ^?
```

### Join tables

A column of the table a `left join` adds can be `null`, and a `coalesce` gives it a default.

```sql tab="user_posts.sql" dialect="all"
select u.name, p.title, coalesce(p.title, '') as label
from users u
left join posts p on p.user_id = u.id
```

```ts twoslash tab="main.ts"
import userPosts from "./user_posts.sql";

const rows = await userPosts.run(db);
//    ^?
```

### Filter by a list

Pass the list as one parameter.


```sql file="users_by_ids.sql" tab="MySQL" tab-group="dialect"
  select :ids::json('{
    "type": "array",
    "items": { "type": "integer" }
  }') as ids
```

### Keep a list's order

Number the list's elements, and sort by the number.

```sql file="users_in_order.sql" tab="Postgres" tab-group="dialect"
-- with ordinality numbers the elements
select u.id, u.name
from unnest(:ids::int[]) with ordinality as i(id, position)
join users u on u.id = i.id
order by i.position
```

```sql file="users_in_order.sql" tab="MySQL" tab-group="dialect"
-- a for ordinality column numbers the elements
with input as (
  select :ids::json('{
    "type": "array",
    "items": { "type": "integer" }
  }') as ids
)
select u.id, u.name
from input, json_table(input.ids, '$[*]' columns (
  position for ordinality,
  id int path '$'
)) as i
join users u on u.id = i.id
order by i.position
```

```sql file="users_in_order.sql" tab="SQLite" tab-group="dialect"
-- json_each numbers the elements as key
with input as (
  select :ids::json('{
    "type": "array",
    "items": { "type": "integer" }
  }') as ids
)
select u.id, u.name
from input, json_each(input.ids) as i
join users u on u.id = i.value
order by i.key
```

```ts twoslash
import usersInOrder from "./users_in_order.sql";

const users = await usersInOrder.run(db, { ids: [3, 1, 2] });
//    ^?
```

### Nest related rows

Build the related rows as JSON in the statement. Reylo types the JSON from the arguments that build it.

```sql file="user_with_posts.sql" tab="Postgres" tab-group="dialect"
select u.id, u.name,
  coalesce((
    select jsonb_agg(jsonb_build_object(
      'id', p.id,
      'title', p.title,
      'at', p.published_at
    ))
    from posts p where p.user_id = u.id
  ), '[]') as posts
from users u
where u.id = :id::int
```

```sql file="user_with_posts.sql" tab="MySQL" tab-group="dialect"
select u.id, u.name,
  coalesce((
    select json_arrayagg(json_object(
      'id', p.id,
      'title', p.title,
      'at', p.published_at
    ))
    from posts p where p.user_id = u.id
  ), json_array()) as posts
from users u
where u.id = :id::int
```

```sql file="user_with_posts.sql" tab="SQLite" tab-group="dialect"
select u.id, u.name,
  (
    select json_group_array(json_object(
      'id', p.id,
      'title', p.title,
      'at', p.published_at
    ))
    from posts p where p.user_id = u.id
  ) as posts
from users u
where u.id = :id::int
```

```ts twoslash
import userWithPosts from "./user_with_posts.sql";

const user = await userWithPosts.run(db, { id: 1 });
//    ^?
```

<Dialect value="SQLite">

SQLite returns the JSON it builds as text, so `posts` is a string.

</Dialect>

### Insert related rows

Users with their posts, in one parameter. The posts find their user by `email`, a unique key.

<DialectTabs>
<Dialect value="Postgres">

Postgres writes both tables in one statement: a `with` inserts the users, and the statement inserts the posts.

```sql file="create_users_with_posts.sql"
with input as (
  select :users::jsonb('{
    "type": "array",
    "items": {
      "type": "object",
      "properties": {
        "name": { "type": "string" },
        "email": { "type": "string", "format": "email" },
        "posts": {
          "type": "array",
          "items": {
            "type": "object",
            "properties": { "title": { "type": "string" } },
            "required": ["title"]
          }
        }
      },
      "required": ["name", "email", "posts"]
    }
  }') as users
),
new_users as (
  insert into users (name, email)
  select u.name, u.email
  from input, jsonb_to_recordset(input.users) as u(name text, email text)
  returning id, email
)
insert into posts (user_id, title)
select n.id, p.title
from input
cross join jsonb_to_recordset(input.users) as u(email text, posts jsonb)
join new_users n on n.email = u.email
cross join jsonb_to_recordset(u.posts) as p(title text)
```

```ts twoslash
  },
];

```

</Dialect>
<Dialect value="MySQL">

```sql title="insert_users.sql"
  name text path '$.name',
```

```sql title="insert_posts.sql"
insert into posts (user_id, title)
with input as (
  select :users::json('{
    "type": "array",
    "items": {
      "type": "object",
      "properties": {
        "email": { "type": "string" },
        "posts": {
          "type": "array",
          "items": {
            "type": "object",
            "properties": { "title": { "type": "string" } },
            "required": ["title"]
          }
        }
      },
      "required": ["email", "posts"]
    }
  }') as users
)
select users.id, u.title
from input, json_table(input.users, '$[*]' columns (
  -- the collation of users.email
  email varchar(255) collate utf8mb4_0900_ai_ci path '$.email',
  nested path '$.posts[*]' columns (title text path '$.title')
)) as u
join users on users.email = u.email
where u.title is not null
```

```ts twoslash
import mysql from "mysql2/promise";
import insertUsers, { type Params } from "./insert_users.sql";
//                         ^?
import insertPosts from "./insert_posts.sql";

const db = mysql.createPool(process.env.DATABASE_URL!);
const users = [
  {
    name: "Ada",
    email: "ada@example.com",
    posts: [{ title: "Notes" }],
  },
];

const conn = await db.getConnection();
try {
  await conn.beginTransaction();
  await insertUsers.run(conn, { users });
  await insertPosts.run(conn, { users });
  await conn.commit();
} catch (error) {
  await conn.rollback();
  throw error;
} finally {
  conn.release();
}
```

A `JSON_TABLE` column takes the connection's collation, `utf8mb4_unicode_ci` under `mysql2`. Comparing it with a column of another collation is an error, so the `email` column names the collation of `users.email`.

### Run statements in a transaction

A transaction, a savepoint or a connection taken from a client is a client too:

```sql file="rename_user.sql" dialect="all"
update users set name = :name::text where id = :id::int
```

<DialectTabs>
<Dialect value="Postgres">

```ts twoslash
import postgres from "postgres";
import getUser from "./get_user.sql";
import renameUser from "./rename_user.sql";

const db = postgres(process.env.DATABASE_URL!);

await db.begin(async (tx) => {
  const user = await getUser.run(tx, { id: 1 });
  await tx.savepoint((sp) =>
    renameUser.run(sp, { id: user!.id, name: "Grace" }),
  );
});
```

</Dialect>

### Insert or update

When the email already exists, the insert updates that row instead. With `returning`, it resolves to the row's id.

```sql file="upsert_user.sql" tab="Postgres" tab-group="dialect"

on conflict (email) do update set name = excluded.name
returning id
```

### Record events of several kinds

A `oneOf` types a JSON parameter as a union. Here a `const` key tells the members apart:

```sql file="record_events.sql" tab="Postgres" tab-group="dialect"
with input as (
  select :events::jsonb('{
    "type": "array",
    "items": {
      "oneOf": [
        {
          "type": "object",
          "properties": {
            "kind": { "type": "string", "const": "click" },
            "x": { "type": "integer" },
            "y": { "type": "integer" }
          },
          "required": ["kind", "x", "y"]
        },
        {
          "type": "object",
          "properties": {
            "kind": { "type": "string", "const": "key" },
            "code": { "type": "string" }
          },
          "required": ["kind", "code"]
        }
      ]
    }
  }') as events
)
insert into events (kind, payload)
select e.value ->> 'kind', e.value
from input, jsonb_array_elements(input.events) as e(value)
```
