```sql title="get_user.sql"
select id, name, email from users where id = :id
```

```ts twoslash title="main.ts"
// Twoslash runs TypeScript 6, which cannot run a content mapper: get_user.d.sql.ts is the module
// reylo's mapper returned for get_user.sql (tsc --runExternalCode, against the schema below).
// @allowArbitraryExtensions
// @filename: get_user.d.sql.ts
import type { Query } from "reylo";
export type Params = { id: number };
export type Values = [id: number];
export type Row = { id: number; name: string; email: string | null };
export declare const sql: "select id, name, email from users where id = :id\n";
export declare const params: readonly ["id"];
declare const query: Query<{ id: number }, { id: number; name: string; email: string | null }, "maybeOne", "postgres", [id: number]>;
export default query;
// @filename: guard.ts
import getUser from "./get_user.sql";
// @ts-expect-error: fails the build if the reylo types stop resolving and the query becomes `any`.
const typed: string = getUser;
// @filename: main.ts
// ---cut---
import postgres from "postgres";
import getUser from "./get_user.sql";

const sql = postgres(process.env.DATABASE_URL!);

const user = await getUser.run(sql, { id: 1 });
```

Every type above comes from the database.

## How it works

Reylo is a [content mapper](https://github.com/microsoft/typescript-go/pull/4712), a feature new in TypeScript 7.1: a package that turns a file TypeScript does not know into a typed module, in the type checker and in the editor. Bundlers have loaded `.sql` files for years, and content mappers are the missing half, so a loader is now type safe from end to end.

```text
get_user.sql  →  reylo  →  your database  →  { id: number; name: string; email: string | null } | null
```

To type a query, Reylo sends it to your running database, which prepares it without running it. The database reports:

- the parameter types
- the column types
- nullability, from `NOT NULL` and outer joins
- the row count, from primary and unique keys

Reylo connects through your project's `postgres`, `pg` or `mysql2`, and keeps each answer in `.reylo/` until the schema changes.

## Setup

Install Reylo and point it at your database, then add it to each tool that loads your code.

### Install

```sh
npm install reylo
npm install -D typescript@next   # content mappers are in the TypeScript 7.1 dev builds
```

Reylo also needs one of these drivers in your project, as a peer dependency, whichever driver your application runs on: `postgres` or `pg` for Postgres, `mysql2` for MySQL. SQLite needs none.

Reylo needs Node 24 or later. It reads `DATABASE_URL` from the environment, or from `.env.local` or `.env` next to `package.json`:

```sh title=".env"
DATABASE_URL=postgres://localhost:5432/app   # mysql://… for MySQL, file:./app.db for SQLite
```

Other settings go in `.reylo.yaml`: see [The project file](/details#the-project-file).

### TypeScript

Add Reylo to `tsconfig.json`:

```jsonc title="tsconfig.json"
{
  "compilerOptions": { /* ... */ },
  "contentMappers": [ // [!code ++]
    { "package": "reylo", "extensions": [".sql"] } // [!code ++]
  ] // [!code ++]
}
```

Type-check with `--runExternalCode`. Without the flag, `tsc` ignores content mappers.

```json title="package.json"
{
  "scripts": {
    "typecheck": "tsc --noEmit --runExternalCode"
  }
}
```

### Runtimes

A preload turns each `.sql` import into a module as it loads:

```sh
node --import reylo/register main.ts
```

Bun and nub read the preload from their config files, so no flag is needed:

```toml title="bunfig.toml"
preload = ["reylo/register"]
```

```jsonc title="nub.jsonc"
{
  "preload": ["reylo/register"]
}
```

## Basic usage

Write the query in a `.sql` file:

```sql title="get_user.sql"
select id, name, email from users where id = :id
```

Import it, and run it with a client from your driver:

```ts title="main.ts"
import postgres from "postgres";
import getUser from "./get_user.sql";

const sql = postgres(process.env.DATABASE_URL!);

const user = await getUser.run(sql, { id: 1 });
// { id: number; name: string; email: string | null } | null
```

The query has a few more members:

```ts
import type { Params, Row } from "./get_user.sql"; // its parameter and row types

await getUser.run(sql, [1]);         // the parameters as an array, in the order of getUser.params

const get = getUser.with(tx);        // bind a client once, such as a transaction
await get({ id: 1 });

getUser.runSync(db, { id: 1 });      // better-sqlite3, node:sqlite and bun:sqlite answer synchronously

getUser.sql;                         // the statement as written
getUser.params;                      // ["id"]
getUser.cardinality;                 // "maybeOne"
```

The sections below go through each kind of statement, from reading one row to writing related rows. Reylo puts no limits on the query: any syntax, any built-in function, *the full expressive power of your SQL dialect*. Each example shows the statement in each dialect and the types Reylo infers: the parameters, and what `run` resolves to.

## Read

### One row

A match on a primary or a unique key is at most one row, so `run` resolves to the row or `null`. The statement and its types are the same in every dialect.

```sql title="find_by_email.sql"
select id, name from users where email = :email
```

```ts
type Params = { email: string };
type Result = { id: number; name: string } | null;
```

### Many rows

A statement that can match more than one row resolves to an array.

<Tabs groupId="dialect" persist items={["Postgres", "MySQL", "SQLite"]}>
<Tab value="Postgres">

```sql title="list_users.sql"
select id, name, role, tags, created_at from users
where role = :role
order by created_at desc
limit :limit offset :offset
```

```ts
type Params = {
  role: "admin" | "member";           // the enum's labels
  limit: number | bigint | string;    // limit and offset take a bigint
  offset: number | bigint | string;
};
type Result = {
  id: number;
  name: string;
  role: "admin" | "member";
  tags: string[];
  created_at: Date;
}[];
```

</Tab>

### Joins

A column from the outer side of a join can be `null`. The statement and its types are the same in every dialect.

```sql title="user_posts.sql"
select u.name, p.title, coalesce(p.title, '') as label
from users u
left join posts p on p.user_id = u.id
```

```ts
type Result = {
  name: string;          // not null in the table
  title: string | null;  // the outer side of a left join
  label: string;         // coalesce with a non-null default
}[];
```

### A list of values

Postgres takes an array. MySQL and SQLite have no array type, so the list is a [JSON parameter](#json-parameters), which the statement reads as rows.

<Tabs groupId="dialect" persist items={["Postgres", "MySQL", "SQLite"]}>
<Tab value="Postgres">

```sql title="users_by_ids.sql"
select id, name from users where id = any(:ids)
```

```ts
type Params = { ids: number[] };
type Result = { id: number; name: string }[];
```

</Tab>
<Tab value="MySQL">

```sql title="users_by_ids.sql"
with input as (
  select :ids::json('{ "type": "array", "items": "int" }') as ids
)
select id, name from users
where id in (
  select j.id from input, json_table(input.ids, '$[*]' columns (id int path '$')) as j
)
```

```ts
type Params = { ids: number[] };
type Result = { id: number; name: string }[];
```

</Tab>
<Tab value="SQLite">

```sql title="users_by_ids.sql"

  select :ids::json('{ "type": "array", "items": "integer" }') as ids

select id, name from users
where id in (select j.value from input, json_each(input.ids) as j)
```


### A list, in its order

Each dialect numbers a list's elements, so the rows can come back in the list's order.

<Tabs groupId="dialect" persist items={["Postgres", "MySQL", "SQLite"]}>
<Tab value="Postgres">

`with ordinality` adds each element's position:

```sql title="users_in_order.sql"
select u.id, u.name
from unnest(:ids::int[]) with ordinality as i(id, position)
join users u on u.id = i.id
order by i.position
```

</Tab>
<Tab value="MySQL">

A `for ordinality` column holds each element's position:

```sql title="users_in_order.sql"
with input as (
  select :ids::json('{ "type": "array", "items": "int" }') as ids
)
select u.id, u.name
from input, json_table(input.ids, '$[*]' columns (position for ordinality, id int path '$')) as i
join users u on u.id = i.id
order by i.position
```

</Tab>
<Tab value="SQLite">

`json_each` gives each element's index as `key`:

```sql title="users_in_order.sql"
with input as (
  select :ids::json('{ "type": "array", "items": "integer" }') as ids
)
select u.id, u.name
from input, json_each(input.ids) as i
join users u on u.id = i.value
order by i.key
```

</Tab>
</Tabs>

```ts
type Params = { ids: number[] };
type Result = { id: number; name: string }[];
```

### Nested rows

Build the related rows as JSON in the statement. Reylo types the JSON from the arguments that build it.

<Tabs groupId="dialect" persist items={["Postgres", "MySQL", "SQLite"]}>
<Tab value="Postgres">

```sql title="user_with_posts.sql"
select u.id, u.name,
  coalesce((
    select jsonb_agg(jsonb_build_object('id', p.id, 'title', p.title, 'at', p.published_at))
    from posts p where p.user_id = u.id
  ), '[]') as posts
from users u
where u.id = :id
```

```ts
type Params = { id: number };
type Result = {
  id: number;
  name: string;
  posts: { id: number; title: string; at: string | null }[];
} | null;
```

</Tab>
<Tab value="MySQL">

```sql title="user_with_posts.sql"
select u.id, u.name,
  coalesce((
    select json_arrayagg(json_object('id', p.id, 'title', p.title, 'at', p.published_at))
    from posts p where p.user_id = u.id
  ), json_array()) as posts
from users u
where u.id = :id
```

```ts
type Params = { id: number };
type Result = {
  id: number;
  name: string;
  posts: { id: number; title: string; at: string | null }[];
} | null;
```

</Tab>
<Tab value="SQLite">

```sql title="user_with_posts.sql"
select u.id, u.name,
  (select json_group_array(json_object('id', p.id, 'title', p.title, 'at', p.published_at))
   from posts p where p.user_id = u.id) as posts
from users u
where u.id = :id
```

```ts
type Params = { id: number };
type Result = {
  id: number;
  name: string;
  posts: string;   // SQLite returns the JSON it builds as text
} | null;
```

</Tab>

### Insert many rows

Pass the rows as one [JSON parameter](#json-parameters). The schema in its cast types the parameter, and Reylo checks every row against it before the statement runs. The database reads the JSON with its own functions, and never sees the schema.

<Tabs groupId="dialect" persist items={["Postgres", "MySQL", "SQLite"]}>
<Tab value="Postgres">

```sql title="create_users.sql"
with input as (
  select :users::jsonb('{
    "type": "array",
    "maxItems": 1000,
    "items": {
      "type": "object",
      "properties": {
        "name": "text",
        "email?": { "type": "text", "format": "email" }
      }
    }
  }') as users
)
insert into users (name, email)
select u.name, u.email
from input, jsonb_to_recordset(input.users) as u(name text, email text)
returning id
```

```ts
type Params = { users: { name: string; email?: string | null }[] };
type Result = { id: number }[];
```

</Tab>
<Tab value="MySQL">

```sql title="create_users.sql"
insert into users (name, email)
with input as (
  select :users::json('{
    "type": "array",
    "maxItems": 1000,
    "items": {
      "type": "object",
      "properties": {
        "name": "text",
        "email?": { "type": "varchar(255)", "format": "email" }
      }
    }
  }') as users
)
select u.name, u.email
```

### Insert related rows

Users with their posts, in one parameter. The posts find their user by `email`, a unique key.

<Tabs groupId="dialect" persist items={["Postgres", "MySQL", "SQLite"]}>
<Tab value="Postgres">

Postgres writes both tables in one statement: a `with` inserts the users, and the statement inserts the posts.

```sql title="create_users_with_posts.sql"
with input as (
  select :users::jsonb('{
    "type": "array",
    "items": {
      "type": "object",
      "properties": {
        "name": "text",
        "email": { "type": "text", "format": "email" },
        "posts": {
          "type": "array",
          "items": { "type": "object", "properties": { "title": "text" } }
        }
      }
    }
  }') as users
),
new_users as (
  insert into users (name, email)
  select u.name, u.email
  from input, jsonb_to_recordset(input.users) as u(name text, email text)
  returning id, email
)
insert into posts (user_id, title)
select n.id, p.title
from input
cross join jsonb_to_recordset(input.users) as u(email text, posts jsonb)
join new_users n on n.email = u.email
cross join jsonb_to_recordset(u.posts) as p(title text)
```

```ts
type Params = { users: { name: string; email: string; posts: { title: string }[] }[] };

```

```sql title="insert_users.sql"
    "type": "array",
```

```ts title="main.ts"
} finally {
  conn.release();
}
```

## Parameters

A parameter is a name after a colon, such as `:id`, and `run` takes an object with one key for each name. Reylo types each parameter from where the statement uses it: a column it is compared with or written to, a function's argument, a cast.

Each parameter appears once in a statement, so one place types it. To use a value twice, select it once in a `with`:

`::` casts a parameter in every dialect. MySQL and SQLite have no `::`, so Reylo writes their own `cast(… as …)`. A JSON parameter's cast also carries its schema: see [JSON parameters](#json-parameters).

## JSON parameters

A JSON parameter carries a schema in its cast, as a string: `:users::jsonb('…')` or `:users::json('…')` on Postgres, `:users::json('…')` on MySQL and SQLite. The schema gives the parameter its TypeScript type, and Reylo checks each value against it before the statement runs. The database never sees the schema: Postgres receives `$1::jsonb`, MySQL `cast(? as json)` and SQLite `?`, and the value is sent as JSON text.

The schema is JSON, shaped as JSON Schema, with your database's type names:

- `type` is `"object"`, `"array"` or a type of the dialect: `"text"`, `"int"` or `"uuid"` on Postgres; `"varchar(255)"` or `"int"` on MySQL; `"text"`, `"integer"`, `"real"`, `"blob"` or `"any"` on SQLite, the types a `strict` table takes.
- A field that needs nothing but its type is written as the type: `"name": "text"`.
- Every key is required. A key that ends in `?` may be left out or be `null`: `"email?": "text"` is `email?: string | null`.
- A key that the schema does not name is ignored, unless its object sets `"additionalProperties": false`.
- A nested object or array is one JSON value, which the statement reads with the database's JSON functions, as in [Insert related rows](#insert-related-rows).

Each database type is typed as JSON carries it: text types and `uuid` as `string`, number types as `number`, `boolean` as `boolean`, `json` and `jsonb` as any JSON value.

The checks are JSON Schema's validation keywords: `format`, `pattern`, `minLength` and `maxLength`; `minimum`, `maximum` and `multipleOf`; `enum` and `const`; `minItems`, `maxItems` and `uniqueItems`. `enum` and `const` narrow the type too. A value that fails a check makes `run` reject before the statement reaches the database, with every issue listed.

## Dialects

Postgres is the reference dialect. MySQL and SQLite type less: see [Dialect limits](/details#dialect-limits).

### Postgres

Reylo prepares the statement on the server and reads the description of its parameters and columns. It then reads the catalog for `NOT NULL`, keys and enum labels.

| What | Where it comes from |
| --- | --- |
| Parameter types | the server's description of the prepared statement |
| Column types | the server's description; an enum as its labels, a domain as its base type |
| Nullability | `NOT NULL` in the catalog, outer joins, the expressions |
| Row count | primary and unique keys, aggregates, `limit 1`, `returning` |
| Nested JSON | `jsonb_build_object`, `jsonb_agg` and `to_jsonb`, typed from their arguments |

### MySQL

Reylo prepares the statement on the server, which reports the column types, `NOT NULL`, and a type for each parameter from its context. Reylo adds the row count and the shape of JSON built in the statement.

| What | Where it comes from |
| --- | --- |
| Parameter types | the server's prepare |
| Column types | the server's prepare |
| Nullability | the server's `NOT NULL` flag |
| Row count | primary and unique keys, aggregates; a write is `void` (MySQL has no `returning`) |
| Nested JSON | `json_object` and `json_arrayagg`, typed from their arguments |

### SQLite

Reylo reads the schema from the database file and prepares the statement against its own copy of SQLite. SQLite then reports where every column and parameter comes from.

| What | Where it comes from |
| --- | --- |
| Parameter types | where SQLite places the parameter: a comparison with a column, an `insert` or `update` column, a `cast`, `limit` and `offset` |
| Column types | the declared type's affinity |
| Nullability | `NOT NULL` in the table, outer joins, Reylo's table of SQLite's built-in functions |
| Row count | unique indexes and `integer primary key` |
| Nested JSON | `string` |
