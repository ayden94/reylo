## Data types

SQLite types values, not columns: a declared type gives a column an affinity, which Reylo types it by, and only a `STRICT` table holds a column to it ([Declared types and STRICT tables](#declared-types-and-strict-tables)). Reylo decodes every value itself, so each type has one form on every driver:

| Declared type, or expression | TypeScript | The value `.run()` returns |
| --- | --- | --- |
| `INTEGER`, `INT`, and any other type with `INT` in its name | `number` | `42` |
| `BIGINT`, `INT8`, `UNSIGNED BIG INT` | `bigint` | `9007199254740993n` |
| `REAL`, `FLOAT`, `DOUBLE` | `number` | `1.5` |
| `TEXT`, `VARCHAR`, and any type with `CHAR`, `CLOB` or `TEXT` | `string` | `"Ada"` |
| `BLOB` | `Uint8Array` | `Uint8Array.of(1, 2, 255)` |
| `BOOLEAN`, `BOOL` | `boolean` | `true` |
| A comparison, `IS NULL`, `IN`, `BETWEEN`, `LIKE`, `GLOB`, `EXISTS`, `NOT`, `AND`, `OR` | `boolean` | `false` |
| `NUMERIC`, `DECIMAL`, `DATE`, `DATETIME`, and any other name | `number \| string` | `1.5`, `"2026-10-20"` |
| No type, or `ANY` in a `STRICT` table | `unknown` | whatever was stored |
| `count(*)`, `length(…)` | `number` | `2` |
| `json_object(…)`, `json_group_array(…)` | the object or array it builds | `{ total: 1250 }` |
| `json_extract(…)`, `->`, `->>` | `unknown` | `1250` |

In each pair below, the SQL is a value and the JavaScript is what `.run()` returns for it: `select <SQL> as v` gives the row `{ v: <JavaScript> }`.

### Declared types and STRICT tables

Reylo types a column by its declared type's affinity, as [SQLite's rule](https://sqlite.org/datatype3.html#determination_of_column_affinity) gives it, which the table above follows. Outside a `STRICT` table, SQLite stores a value of any class in any column, and the type says so:

```ts twoslash tab="main.ts"
import loose from "./lite_loose.sql";

const rows = await loose.run(db);
//    ^?
```

```sql tab="lite_loose.sql" dialect="sqlite"
-- users is not strict: name and nick may hold a BLOB
select name, nick from users
```

- **A `STRICT` table** holds each value to its declared type, so the types above are exact: declare tables `strict` wherever you can. It takes no `BOOLEAN`, `BIGINT`, `DATE` or `NUMERIC` column, so a flag there is an `INTEGER`, a `number`.
- **A `CHECK`** narrows no type, since `pragma ignore_check_constraints` lets a connection write past it: `check (role in ('admin', 'member'))` leaves `role` a `string`, and a JSON Schema check leaves a document a `string`.

### Integers

The declared width decides, as on Postgres and MySQL: a column declared `BIGINT`, `INT8` or `UNSIGNED BIG INT` is a JavaScript `bigint`, exact to SQLite's 64 bits, and every other integer is a `number`, `INTEGER`, `INT`, the rowid and `count(*)` included:

```ts twoslash tab="main.ts"
import userOrders from "./lite_user_orders.sql";

const rows = await userOrders.run(db);
//    ^?
```

```sql tab="lite_user_orders.sql" dialect="sqlite"
select u.id, u.github_id, count(o.id) as orders
from users u
left join orders o on o.user_id = u.id
group by u.id
```

<Rules>

**What stays a `bigint`**

A `BIGINT` column stays a `bigint` through a subquery, a view, `min()`, `max()`, `coalesce()` and `CASE`. These pairs read `users.github_id`, which holds 9007199254740993.

<Pairs>

- `max(github_id)` → `9007199254740993n`
- `coalesce(github_id, 0)` → `9007199254740993n`
- `(select github_id from users)` → `9007199254740993n`

</Pairs>

**What SQLite computes from it**

What SQLite computes from a `BIGINT`, such as `github_id + 1`, `abs(github_id)` or `sum(github_id)`, is an integer like `count(*)`, a `number`. Here `users.github_id` holds 41.

<Pairs>

- `github_id + 1` → `42`
- `sum(github_id)` → `41`

</Pairs>

**Past what a `number` holds**

A `number` past ±(2^53 − 1) is an error that names its column, never a rounded number. Declare the column `BIGINT`, or cast the value to text: `cast(max(id) as text)`. Some drivers round a `BIGINT` too ([Drivers](#drivers)).

<Pairs>

- `9007199254740993` → `throws DecodeError`
- `cast(9007199254740993 as text)` → `"9007199254740993"`

</Pairs>

</Rules>

### Decimals

SQLite has no decimal type: a `NUMERIC` or `DECIMAL` column holds whatever the row stored, so it is `number | string`. Keep an exact amount as an integer of its smallest unit, as `orders.total_cents` does, which here holds 1250 and 1251:

<Pairs>

- `sum(total_cents)` → `2501`
- `avg(total_cents)` → `1250.5`

</Pairs>

### Dates and times

SQLite has no date or time type. A date is the text, the number or the real you store, and its type is its column's: a `TEXT` column's date is a `string`, as SQLite's own date functions write it:

```ts twoslash tab="main.ts"
import orderDates from "./lite_order_dates.sql";

const order = await orderDates.run(db, { id: 1 });
//    ^?
```

```sql tab="lite_order_dates.sql" dialect="sqlite"
select placed_at, ships_on from orders where id = :id
```

<Rules>

**Instants as ISO 8601 text**

Store an instant as ISO 8601 text in UTC with `Z`, as `strftime('%Y-%m-%dT%H:%M:%fZ', 'now')` writes it, which `Temporal.Instant.from()` and `new Date()` read. SQLite's `current_timestamp` and `datetime()` write UTC with no zone, which a reader can't tell from local time.

<Pairs>

- `strftime('%Y-%m-%dT%H:%M:%fZ', '2026-10-20 10:00:00')` → `"2026-10-20T10:00:00.000Z"`
- `datetime('2026-10-20T10:00:00.000Z')` → `"2026-10-20 10:00:00"`

</Pairs>

**Columns declared `DATE`**

A column declared `DATE` or `DATETIME` has `NUMERIC` affinity, so it holds a number or a text, `number | string`. Declare it `TEXT`, or `INTEGER` for Unix time.

</Rules>

### Truth values

SQLite has no boolean type, and computes a truth value as 1 or 0. Reylo makes every truth value the statement computes a `boolean`, and a column declared `BOOLEAN` or `BOOL`:

```ts twoslash tab="main.ts"
import userFlags from "./lite_user_flags.sql";

const rows = await userFlags.run(db);
//    ^?
```

```sql tab="lite_user_flags.sql" dialect="sqlite"
select id, active, name like 'A%' as starts_with_a from users
```

<Rules>

**What counts**

A truth value the statement computes is a comparison, `IN`, `BETWEEN`, `EXISTS`, `IS`, `NOT`, `AND`, `OR`, `like`, `glob`, `regexp` and `match`, and a `CASE`, `coalesce`, `ifnull`, `iif` or subquery whose every value is one. A `BOOLEAN` column stays one through a subquery or a view.

<Pairs>

- `iif(1 = 1, 0 = 1, 1 = 1)` → `false`
- `(select active from users)` → `true`

</Pairs>

**Values other than 0 and 1**

SQLite holds a `BOOLEAN` column to nothing, so it may hold 2, `'yes'` or a `BLOB`. Reylo reads 0 and 1 as `false` and `true` and refuses any other value, naming its column. Here `users.active` holds 2:

<Pairs>

- `active` → `throws DecodeError`
- `active + 0` → `2`

</Pairs>

</Rules>

### JSON

SQLite has no JSON type: a stored document is `TEXT`, a `string`. JSON the statement builds with `json_object`, `json_array`, `json_group_array` or `json_group_object` is typed from its arguments and comes back parsed:

```ts twoslash tab="main.ts"
import orderSummaries from "./lite_order_summaries.sql";

const rows = await orderSummaries.run(db);
//    ^?
```

```sql tab="lite_order_summaries.sql" dialect="sqlite"
select u.name,
  json_object('total_cents', o.total_cents, 'active', u.active) as summary
from orders o
join users u on u.id = o.user_id
```

<Rules>

**Values inside a document**

Inside a document a value is what SQLite writes in JSON: a truth value is `1` or `0`, and an integer is a number, which `JSON.parse` rounds past 2^53.

<Pairs>

- `json_object('a', 1 = 1)` → `{ a: 1 }`
- `json_object('n', 9007199254740993)` → `{ n: 9007199254740992 }`

</Pairs>

**Built JSON inside built JSON**

Built JSON nests inside other built JSON through `coalesce`, `case` and a scalar subquery.

<Pairs>

- `json_object('n', (select json_object('a', 1)))` → `{ n: { a: 1 } }`
- `json_object('n', case when 1 then json_object('a', 1) end)` → `{ n: { a: 1 } }`

</Pairs>

**Where it stops being JSON**

Through a subquery's or a view's column, or `lag`, SQLite no longer marks a value as JSON, so Reylo types it `unknown`; a cast keeps the mark on SQLite 3.53 but not on Turso's engine. Build the JSON in the query that returns it.

<Pairs>

- `json_object('n', (select j from (select json_object('a', 1) as j)))` → `{ n: "{\"a\":1}" }`

</Pairs>

**Over no rows**

A `json_group_array` over no rows is `[]`, never `null`.

<Pairs>

- `(select json_group_array(id) from users where 0)` → `[]`

</Pairs>

**Reading a document**

What `json_extract`, `->` and `->>` return is `unknown`, since it depends on the document.

<Pairs>

- `json_extract('{"a":1}', '$.a')` → `1`
- `'{"a":"x"}' ->> '$.a'` → `"x"`

</Pairs>

</Rules>

### Functions

SQLite says nothing of a function's result, so Reylo keeps a table of SQLite's built-in functions: `count` is a non-null integer, `coalesce` takes its arguments' type, `upper` is text that is `NULL` only where its argument is.

<Rules>

**Functions that answer `NULL`**

A function that SQLite answers with `NULL` for some non-null arguments is `| null`: the date and time functions, for text they cannot read, and the math functions with a domain (`sqrt`, `ln`, `acos`, …) outside it. So `date(placed_at)` is `string | null`, and `date('now')` a `string`.

<Pairs>

- `date('not a date')` → `null`
- `date('2026-10-20', '+1 fortnight')` → `null`
- `sqrt(-1)` → `null`

</Pairs>

</Rules>

- **A built-in function the table lacks**, such as `unhex`, is `unknown`. Cast its result to type it: `cast(unhex(hash) as blob)`.
- **Your app's SQLite** may be older than Reylo's: libSQL carries 3.45.1, which has no `json_pretty`. So the type check prepares each statement again on each of `better-sqlite3`, `@libsql/client`, `sqlite3` and `@tursodatabase/database` your `package.json` lists, and reports what one refuses with its message. It cannot ask `bun:sqlite`, Cloudflare D1 or a Durable Object.

## Nullability

A column is `| null` unless Reylo infers it never is. SQLite's own check says "may be null" of everything but a literal or a column, so Reylo reads the schema and the statement:

- **A table's column** is non-null where it is declared `NOT NULL`.
- **An outer join** makes the joined table's columns nullable, by SQLite's own mark on the join.
- **A test in the `where`** that fails on `NULL` makes the column non-null: `where nick is not null`, `where lower(nick) = :nick`, and a `left join`'s column tested in the `where`.
- **An expression** is non-null by Reylo's table of SQLite's functions: `length(name)`, `coalesce(nick, name)`, `name || '!'` and `id + 1` over non-null inputs, `count`. A division is `| null`, since SQLite answers `NULL` for a division by zero. Arithmetic on a `REAL` with no answer is the one exception ([Limits](#limits)).
- **An aggregate** other than `count` is `NULL` over no rows.

```ts twoslash tab="main.ts"
import nicknames from "./lite_nicknames.sql";

const rows = await nicknames.run(db);
//    ^?
```

```sql tab="lite_nicknames.sql" dialect="sqlite"
select upper(nick) as shout, coalesce(nick, name) as label
from users
```

A test in the `where` shows the joined row exists, so its columns are non-null; a window function is typed like any other, `lag` nullable on the first row:

```ts twoslash tab="main.ts"
import shipped from "./lite_shipped.sql";

const rows = await shipped.run(db);
//    ^?
```

```sql tab="lite_shipped.sql" dialect="sqlite"
select u.name, o.total_cents, o.ships_on
from users u
left join orders o on o.user_id = u.id
where o.ships_on is not null
```

```ts twoslash tab="main.ts"
import orderGaps from "./lite_order_gaps.sql";

const rows = await orderGaps.run(db);
//    ^?
```

```sql tab="lite_order_gaps.sql" dialect="sqlite"
select id, total_cents,
  lag(total_cents) over (order by id) as previous_total,
  row_number() over (order by id) as n
from orders
```

Where you know more than Reylo can infer, say it in the statement: `coalesce(x, …)` gives a default, and a `where x is not null` test both filters and makes the column non-null.

## Cardinality

How many rows `.run()` resolves to comes from what Reylo infers the statement can return:

| Resolves to | `cardinality` | On SQLite, when the statement |
| --- | --- | --- |
| `Row` | `one` | is an aggregate without a `group by`, `values` of one row, or inserts one row and has `returning`, an `on conflict do update` included |
| `Row \| null` | `maybeOne` | matches every column of a primary key, an `integer primary key` or a unique index with `=`, through joins on the joined table's key; has `limit 1`; is a `distinct` or `group by` over values the `where` pins; or is an `update` or `delete` by key with `returning` |
| `void` | `none` | is an `insert`, `update`, `delete` or `replace` without `returning` |
| `Row[]` | `many` | is anything else |

What counts for nothing on SQLite:

- **A unique index on an expression, or with a `where`.** A statement with `where lower(email) = :email` is `Row[]`, whatever index `lower(email)` has.
- **A key that SQLite converts.** SQLite gives a numeric side's affinity to a `TEXT` or untyped key, so `where code = cast(:code as integer)` matches `'1'` and `'01'`.
- **A key compared under another collation.** SQLite compares under the left side's collation, so a `NOCASE` column on the left of a plain key, `r.k = c.code`, meets `'x'` and `'X'`.
- **A declared column named `rowid`**, which is no rowid.

## Parameters

### Placeholders

Write each parameter as `:name`, or as SQLite's `@name` or `$name`, one prefix per statement, and `.run()` takes an object keyed by the name alone. SQLite's `?` or `?1` works too, never beside a name, keyed by number, `{ 1: 42 }`.

### What a parameter takes

Every value `.run()` returns goes back in as a parameter of its type, on every driver, so a row can be passed straight to the next statement:

| Affinity | A parameter takes |
| --- | --- |
| `INTEGER` | `number` |
| A `BIGINT`, `INT8` or `UNSIGNED BIG INT` column | `number` or `bigint` |
| `REAL` | `number` |
| `TEXT` | `string` |
| `BLOB` | `Uint8Array` |
| `NUMERIC`, a `BOOLEAN` or `DATE` column's included | `number`, `string` or `boolean` |
| A typed JSON parameter | what its schema admits |

### Parameters without a type

SQLite types a parameter only where its own reading of the statement places one:

- compared with a typed expression, or as an element of a row value compared with a typed one (`(created_at, id) < (:at, :id)`)
- an `insert`'s or `update`'s column
- a `cast`, arithmetic, `limit` and `offset`, `in`, `between`, and a `case` arm
- an argument of a built-in function from Reylo's table (`lower(:s)` is text, `abs(:n)` a number, `coalesce(:a, 0)` an integer)

Anywhere else, such as a bare `select :x` or `:x is null`, the parameter is `unknown` until a cast types it:

```ts twoslash tab="main.ts"
import echo, { type Params } from "./lite_echo.sql";
//                  ^?
```

```sql tab="lite_echo.sql" dialect="sqlite" strict="false"
select :value as value, :count::int as count
```

By default such a parameter is an error in the type check, which asks for a cast; [`strict_params: false`](/#strict_params) in `.reylo.yaml` leaves it `unknown`, as above.

### Parameters that may be null

A parameter takes `null` in two places:

- as the first argument of `coalesce` or `ifnull`, with a cast or without;
- written whole, with no cast, to a column that may hold `NULL`, one that is not `NOT NULL` and that no `check (… is not null)` holds.

```ts twoslash tab="main.ts"
import addOrder, { type Params } from "./lite_add_order.sql";
//                      ^?
```

```sql tab="lite_add_order.sql" dialect="sqlite"
insert into orders (user_id, total_cents, ships_on)
values (:user_id, :total_cents, :ships_on)
```

A cast is the parameter's whole type, so `:email::text` never takes `null`, and a test for null (`:p is null`, `:p is col`) makes nothing nullable.

### Casts

SQLite has no `::`, so Reylo writes `:p::type` as SQLite's `CAST` and checks the value against the type before the statement runs, since SQLite's `CAST` never fails: `CAST('abc' AS INTEGER)` is 0. SQLite's own `cast(:p as …)` works too.

| You write | SQLite runs |
| --- | --- |
| `::int`, `::integer`, `::bigint` | `CAST(? AS INTEGER)` |
| `::real`, `::float`, `::double precision` | `CAST(? AS REAL)` |
| `::text`, `::varchar(20)` | `CAST(? AS TEXT)` |
| `::numeric`, `::decimal` | `CAST(? AS NUMERIC)` |
| `::date`, `::time`, `::timestamp`, `::uuid` | `CAST(? AS TEXT)`, since SQLite's `CAST` to a date reads `'2026-10-12'` as 2026 |
| `::blob` | `CAST(? AS BLOB)` |
| `::json`, `::jsonb` | `json(?)`, `jsonb(?)` |

- The check refuses a number that is no integer for `::int`, and a value out of SQLite's 64-bit range, before the statement runs.
- A `::boolean` cast is an error: SQLite's `CAST` to a boolean reads a value as the number it starts with. Pass 1 or 0 and write `::integer`.
- SQLite has no arrays, so a `::text[]` cast is an error.

## Drivers

Reylo gives each value of its own query its type itself, so a setting of yours on the database neither reaches Reylo's query nor is changed by it. The drivers differ only on integers past 2^53:

| Driver | Past 2^53 |
| --- | --- |
| `better-sqlite3`, `node:sqlite`, `bun:sqlite`, Turso's engine | Exact |
| libSQL | Refused by libSQL itself, with a `RangeError` that names no column, at its default `intMode`; exact with `intMode: "bigint"` or `"string"` |
| `sqlite3`, `sqlite`, Cloudflare D1 and Durable Objects, `Bun.sql` without `safeIntegers` | Rounded by the driver, which Reylo refuses, in a `BIGINT` column too |

- The `sqlite3` and `sqlite` drivers bind a `bigint` as `NULL`, and a Durable Object refuses one, so Reylo refuses a `bigint` parameter past 2^53 there unless it is written to a `BIGINT` column.
- With libSQL's `intMode: "string"`, a value Reylo types `unknown` that SQLite stored as an integer comes back as its digits, since libSQL gives nothing to tell it from text.
- The drivers `better-sqlite3`, `node:sqlite`, `bun:sqlite` and the `Database` of `@tursodatabase/database/compat` take `.runSync()` too, which returns the result itself, so it works inside their `db.transaction(fn)`, as a Durable Object's `ctx.storage.sql` does inside `ctx.storage.transactionSync(fn)`, and so does a Drizzle database over `better-sqlite3`, with the transaction its `.transaction()` passes.
- Each driver takes its transactions too: libSQL's `.transaction()`, the handle Turso's `.transactionAsync()` passes its function, `Bun.sql`'s `.begin()` and `.savepoint()`, D1's `.withSession()` sessions, and the `.transaction()` of a Drizzle database over libSQL.
- On Bun 1.4.3, `Bun.sql` returns no rows for a statement whose text holds a `"` inside a single-quoted string, such as `json_extract('{"a":1}', '$.a')`, so `.run()` throws "Expected exactly one row, got 0" where one row is expected. Pass the document as a parameter: `json_extract(:doc::text, '$.a')`.

The type check needs no driver: it reads the schema through `node:sqlite`, which Node has built in since 22.5.

## Limits

The edges of what Reylo types on SQLite, each with what to write instead:

- **A declared type outside a `STRICT` table**, which SQLite does not hold a value to. Declare tables `strict`.
- **A function your application registers, or an extension's.** Reylo prepares the statement in its own SQLite, which lacks the function, so the type check fails with "no such function: slugify", cast or not. Keep the call out of the `.sql` file and apply it in TypeScript to what `.run()` returns.
- **A table in an attached database.** The type check reads one database file, and an `ATTACH` happens on your app's connection at run time, so `select … from other.users` is an error: the database has no schema `other`. A `TEMP` table is the same.
- **A virtual table's module.** Reylo's SQLite has FTS3, FTS4, FTS5, R-tree, Geopoly and `dbstat`, so a schema that uses one is read, and the type check does not ask whether your driver's SQLite has the module.
- **Arithmetic on a `REAL` that has no answer.** SQLite answers `NULL` where a real's arithmetic is not a number, and Reylo types it non-null: `+`, `-` and `*` over non-null values, and `/` and `%` by a literal other than 0.
  - Such a value is `null` where the type says `number`: `1e999 * 0`, `price - price` where `price` holds `1e999`, and `5 % 0.5`, whose divisor `%` reads as the integer 0.
  - Write `coalesce(price * qty, 0)` where a `REAL` may hold an infinity. An overflow is no such case: `9e307 * 9e307` is `Infinity`.
- **A statement nested deeper than 350 expressions**, which is SQLite's error, "Expression tree is too large".
