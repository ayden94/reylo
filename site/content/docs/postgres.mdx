## Data types

Reylo decodes every value itself, so each SQL type has one TypeScript type and one form on every driver:

| SQL type | TypeScript | The value `.run()` returns |
| --- | --- | --- |
| `smallint`, `integer`, `oid` | `number` | `42` |
| `bigint`, `bigserial`, `count(*)` | `bigint` | `9007199254740993n` |
| `real`, `double precision` | `number` | `1.1` |
| `numeric`, `money` | `string` | `"12.50"`, `"$1.50"` |
| `text`, `varchar`, `char`, `uuid` | `string` | `"Ada"` |
| `boolean` | `boolean` | `true` |
| `date` | `string` | `"2026-10-20"` |
| `timestamp` | `string` | `"2026-10-20T10:00:00.123456"` |
| `timestamptz` | `string` | `"2026-10-20T08:00:00.123456Z"` |
| `time`, `timetz`, `interval` | `string` | `"10:00:00"`, `"1 day 02:03:04"` |
| `json`, `jsonb` | `unknown` | `{ a: 1 }` |
| `json`, `jsonb` a JSON Schema `CHECK` holds | what the schema admits | `{ x: 10, y: 20 }` |
| JSON the statement builds (`jsonb_build_object`, `jsonb_agg`) | the object or array it builds | `{ total: 12.5 }` |
| `bytea` | `Uint8Array` | `Uint8Array.of(1, 2, 255)` |
| An array | an array of its element type | `["math", "poetry"]` |
| An enum | the union of its labels | `"admin"` |
| A domain | its base type | its base type's |
| A row value | `string` | `"(1,Ada)"` |
| Every other type (`inet`, ranges, `point`, `tsvector`, `xml`, …) | `string` | `"[1,5)"` |

In each pair below, the SQL is a value and the JavaScript is what `.run()` returns for it: `select <SQL> as v` gives the row `{ v: <JavaScript> }`.

### Integers

A `bigint` is a JavaScript `bigint`, and so is `count(*)`, which Postgres types `bigint`. Cast in the statement where you want a `number`:

```ts twoslash tab="main.ts"
import countOrders from "./pg_count_orders.sql";

const counts = await countOrders.run(db);
//    ^?
```

```sql tab="pg_count_orders.sql"
select count(*) as total, count(*)::int as total_number
from orders
```

The `sum()` of an `integer` column is a `bigint`, and of a `bigint` or a `numeric` a `numeric`, so a `string`:

<Pairs>

- `sum(2::integer)` → `2n`
- `sum(2::bigint)` → `"2"`
- `sum(2.5::numeric)` → `"2.5"`

</Pairs>

### Decimals

A `numeric` is its exact text, with the column's scale, and so is an `avg()`. A `money` is its text in the server's currency format:

<Pairs>

- `12.50::numeric` → `"12.50"`
- `avg(2::integer)` → `"2.0000000000000000"`
- `1.50::money` → `"$1.50"`

</Pairs>

### Dates and times

No value is a `Date`. A `timestamptz` is the instant in UTC, in ISO 8601 with a `Z`, and every type without a zone is the text Postgres writes, with a `T` between the date and the time of a `timestamp`:

```ts twoslash tab="main.ts"
import orderDates from "./pg_order_dates.sql";

const order = await orderDates.run(db, { id: 1 });
//    ^?
```

```sql tab="pg_order_dates.sql"
select placed_at, ships_on from orders where id = :id
```

Where your runtime has `Temporal`, `Temporal.Instant.from()` reads the instant, and `Temporal.PlainDate.from()` the date. Each text goes back in as a parameter as it is ([What a parameter takes](#what-a-parameter-takes)).

<Rules>

**Fractions of a second**

The fraction is the server's, to the microsecond, with its trailing zeros dropped, and none for a whole second.

<Pairs>

- `'2026-10-20 10:00:00.123456+00'::timestamptz` → `"2026-10-20T10:00:00.123456Z"`
- `'2026-10-20 10:00:00.5+00'::timestamptz` → `"2026-10-20T10:00:00.5Z"`
- `'2026-10-20 10:00:00+00'::timestamptz` → `"2026-10-20T10:00:00Z"`

</Pairs>

**Infinity**

The values `infinity` and `-infinity` stay those words, in every date and time type, so `Temporal` cannot read them.

<Pairs>

- `'infinity'::timestamptz` → `"infinity"`
- `'-infinity'::date` → `"-infinity"`

</Pairs>

**Years past 9999 or before 1 AD**

A `timestamptz` takes ISO 8601's extended year, as `Temporal.Instant` writes it. A `date` or a `timestamp` keeps Postgres's text.

<Pairs>

- `'12344-12-31 18:30:00+00'::timestamptz` → `"+012344-12-31T18:30:00Z"`
- `'0002-06-01 12:00:00+00 BC'::timestamptz` → `"-000001-06-01T12:00:00Z"`
- `'0002-06-01 BC'::date` → `"0002-06-01 BC"`

</Pairs>

**Times and intervals**

A `time`, a `timetz` and an `interval` are the text Postgres writes at its default `DateStyle` and `IntervalStyle`, so a session that sets others gets the text they write.

<Pairs>

- `'10:00:00+02'::timetz` → `"10:00:00+02"`
- `'1 day 02:03:04'::interval` → `"1 day 02:03:04"`

</Pairs>

</Rules>

### JSON

A `json` or `jsonb` value is `unknown` unless a JSON Schema `CHECK` holds the column or the statement builds it. Here `events.payload` is what its schema admits, and `kind` the union its `CHECK` allows:

```ts twoslash tab="main.ts"
import events from "./pg_events.sql";

const rows = await events.run(db);
//    ^?
```

```sql tab="pg_events.sql"
select kind, payload from events
```

JSON the statement builds with `jsonb_build_object`, `json_build_object`, `jsonb_agg`, `json_agg` or `to_jsonb` of a whole row is typed from its arguments, each value as JSON writes it:

```ts twoslash tab="main.ts"
import orderSummaries from "./pg_order_summaries.sql";

const rows = await orderSummaries.run(db);
//    ^?
```

```sql tab="pg_order_summaries.sql"
select u.name,
  jsonb_build_object(
    'total', o.total,
    'placed_at', o.placed_at,
    'paid', o.paid
  ) as summary
from orders o
join users u on u.id = o.user_id
```

Through an aggregate the schema's type holds, and a whole row as JSON is typed column by column, an enum's labels included:

```ts twoslash tab="main.ts"
import eventsByKind from "./pg_events_by_kind.sql";

const groups = await eventsByKind.run(db);
//    ^?
```

```sql tab="pg_events_by_kind.sql"
select kind, jsonb_agg(payload order by id) as payloads
from events
group by kind
```

```ts twoslash tab="main.ts"
import userRow from "./pg_user_row.sql";

const row = await userRow.run(db, { id: 1 });
//    ^?
```

```sql tab="pg_user_row.sql"
select to_jsonb(u) as "user" from users u where u.id = :id::int
```

<Rules>

**Values inside a document**

Inside a document a value is what JSON writes: integers and `numeric` are numbers, which `JSON.parse` rounds past 2^53, a `timestamptz` is its text in the session's time zone, here `America/Los_Angeles`, and a `bytea` its hex text.

<Pairs>

- `jsonb_build_object('n', 9007199254740993::bigint)` → `{ n: 9007199254740992 }`
- `jsonb_build_object('n', 12.50::numeric)` → `{ n: 12.5 }`
- `jsonb_build_object('at', '2026-10-20 08:00:00+00'::timestamptz)` → `{ at: "2026-10-20T01:00:00-07:00" }`
- `jsonb_build_object('b', '\x0102ff'::bytea)` → `{ b: "\\x0102ff" }`
- `json_build_object('u', row(1, 'Ada'))` → `{ u: { f1: 1, f2: "Ada" } }`

</Pairs>

**Aggregates over no rows**

Over no rows, `jsonb_agg` is `null`, and its type says so: `coalesce(jsonb_agg(…), '[]')` is the array alone. Under any other default the value may be that default, so the column is `unknown`.

<Pairs>

- `jsonb_agg(1) filter (where false)` → `null`
- `coalesce(jsonb_agg(1) filter (where false), '[]')` → `[]`

</Pairs>

</Rules>

- **Where the schema's type reaches:** a bare read of the column, through a view or a subquery too, the column inside JSON the statement builds, a whole stored row (`jsonb_agg(e)`), and a parameter written whole to the column.
- **Where it stops:** an expression over the column (`payload -> 'x'`), a column under a `union`, a `CHECK` added `NOT VALID`, and one value turned to JSON by `to_jsonb` are `unknown`.
- **Through a `with` query or a derived table,** JSON keeps its type where the statement reads its column as it is, alone or inside JSON it builds, and an array under `coalesce(…, '[]')`. A `union` in the query, a `lateral` one or a `*` over it is `unknown`.
- **The validators Reylo reads** are pg_jsonschema's `jsonb_matches_schema` and `json_matches_schema` and those of `jsonschema`, `postgres-json-schema`, `is_jsonb_valid` and `json_schema_validate`, each by the keywords and the draft it enforces.

### Arrays

An array is a JavaScript array of its element's type, an enum's and a domain's included:

```ts twoslash tab="main.ts"
import orderIds from "./pg_order_ids.sql";

const rows = await orderIds.run(db);
//    ^?
```

```sql tab="pg_order_ids.sql"
select u.name, u.tags, array_agg(o.id) as order_ids
from users u
left join orders o on o.user_id = u.id
group by u.id
```

<Rules>

**`NULL` elements**

Postgres lets any array hold `NULL`, whatever the column's `NOT NULL` says, so a `text[]` column is typed `(string | null)[]`. An array the statement builds from values that can't be `NULL`, as `array[id]` over a primary key, is typed `number[]`.

<Pairs>

- `'{a,NULL}'::text[]` → `[ "a", null ]`

</Pairs>

**Several dimensions**

Postgres does not record how many dimensions an array has, so a two-dimensional `int[]` is typed `(number | null)[]` and comes back as nested arrays.

<Pairs>

- `'{{1,2},{3,4}}'::int[]` → `[ [ 1, 2 ], [ 3, 4 ] ]`

</Pairs>

</Rules>

### Enums and domains

An enum is the union of its labels, and so is a `text` or `varchar` column whose `CHECK` keeps it to a list of strings (`kind in ('click', 'key')`). A domain is its base type: `orders.total`, an `amount`, is a `numeric`, so a `string`.

<Pairs>

- `'{admin,member}'::user_role[]` → `[ "admin", "member" ]`

</Pairs>

A domain over `jsonb` whose `CHECK` holds it to a JSON Schema is what the schema admits, and a `CHECK` added `NOT VALID` narrows nothing, since rows written before it may not hold.

## Nullability

A column is `| null` unless Reylo infers it never is. On Postgres, Reylo reads the catalog and the statement:

- **A table's column** is non-null where its `NOT NULL` is valid and holds in every table that inherits from it.
- **An outer join** makes the joined table's columns nullable: the right side of a `left join`, the left side of a `right join`, both sides of a `full join`. A table on both sides is told apart by its alias, so `e.name` of `employees e left join employees m on m.id = e.manager_id` keeps its `NOT NULL`.
- **A test in the `where`** that fails on `NULL` makes the column non-null, and a later inner join's `on` shows the joined row exists: `where o.total > 0`, `where email is not null`, `where lower(email) = :email`.
- **An expression** is non-null when Reylo's rules infer it:
  - a literal, a cast, `count`, `exists` and `is null`;
  - concatenation with `||`, a comparison, arithmetic, `like` and the other pattern matches, and the bit, containment and JSON key operators (`&`, `@>`, `&&`, `?`) over non-null operands;
  - the values `generate_series` gives, and those of `unnest(array[…])` where every element written is a non-null value and not an array;
  - a built-in function that returns `NULL` only for a `NULL` argument (`length`, `lower`, `round`, …);
  - a `coalesce` with a non-null argument;
  - a `case` whose branches and `else` are all non-null.
- **An aggregate** other than `count` is `NULL` over no rows, so it is nullable without a `group by`. With one, every group has a row:
  - the aggregates that write a `NULL` into what they build, `array_agg`, `json_agg`, `jsonb_agg` and `jsonb_object_agg`, are non-null;
  - those that skip a `NULL`, `sum`, `max`, `string_agg` and the others, are non-null where their argument is;
  - an aggregate with a `filter` stays nullable, since the filter can leave a group no rows.
- **A table's whole row** (`select e`, `jsonb_agg(e)`) is never `NULL` unless an outer join nulls it, and keeps its columns' `NOT NULL` and their `CHECK` lists.
- **A scalar subquery** is non-null only when it is one row of a non-null value: an aggregate without a `group by`, as `(select count(*) …)` is, or a `select` with no `from`, as `(select 1)` is.
- **A column of a `union`** is non-null when it is in every arm.
- **A column of a `with` query or a derived table** is as nullable as that query's own statement makes it.
- **An operator, function or cast your database defines**, or an extension does, tells Reylo nothing: the rules stand down wherever Postgres could pick one of those over the built-in.

```ts twoslash tab="main.ts"
import userTotals from "./pg_user_totals.sql";

const rows = await userTotals.run(db);
//    ^?
```

```sql tab="pg_user_totals.sql"
select u.name, o.total, coalesce(o.paid, false) as paid
from users u
left join orders o on o.user_id = u.id
```

A test in the `where` shows the joined row exists, so its columns are non-null; a window function is typed like any other, `lag` nullable on the first row:

```ts twoslash tab="main.ts"
import paidOrders from "./pg_paid_orders.sql";

const rows = await paidOrders.run(db);
//    ^?
```

```sql tab="pg_paid_orders.sql"
select u.name, o.total, o.placed_at
from users u
left join orders o on o.user_id = u.id
where o.paid
```

```ts twoslash tab="main.ts"
import orderGaps from "./pg_order_gaps.sql";

const rows = await orderGaps.run(db);
//    ^?
```

```sql tab="pg_order_gaps.sql"
select id, placed_at,
  placed_at - lag(placed_at) over (order by placed_at) as since_previous,
  row_number() over (order by placed_at) as n
from orders
```

Where you know more than Reylo can infer, say it in the statement: `coalesce(x, …)` gives a default, and a `where x is not null` test both filters and makes the column non-null.

## Cardinality

How many rows `.run()` resolves to comes from what Reylo infers the statement can return:

| Resolves to | `cardinality` | On Postgres, when the statement |
| --- | --- | --- |
| `Row` | `one` | is an aggregate without a `group by`, or inserts one row with `values (…)` and has `returning`, an `on conflict do update` included |
| `Row \| null` | `maybeOne` | matches every column of a primary key or unique index with `=`, through joins on the joined table's key; has `limit 1` or `fetch first 1 row only`; is a `distinct` or `group by` over values the `where` pins; is an `update` or `delete` by key with `returning`; or inserts one row with `on conflict do nothing` and `returning` |
| `void` | `none` | is an `insert`, `update`, `delete` or `merge` without `returning` |
| `Row[]` | `many` | is anything else |

A unique index on an expression counts when the statement compares the same expression, and a partial unique index when the `where` holds its predicate:

```ts twoslash tab="main.ts"
import userByEmail from "./pg_user_by_email.sql";

const user = await userByEmail.run(db, { email: "Ada@example.com" });
//    ^?
```

```sql tab="pg_user_by_email.sql"
select id, name from users where lower(email) = lower(:email)
```

- The expression is matched as Postgres stores it in the index. An index over a domain column stores a cast, `lower((email)::text)`, and the statement must write it the same way to match.
- A partial unique index without its predicate in the `where` counts for nothing: `where slug = :slug` over an index on `slug` `where not deleted` is `Row[]`.
- Part of a composite key counts for nothing, and neither does a `having`, or an `insert … select … returning`.

## Parameters

### Placeholders

Write each parameter as `:name`, which Reylo sends as `$1`, `$2`, …. Postgres's own `$1` works too, never beside `:name`, and `.run()` then takes an object keyed by number, `{ 1: 42 }`.

### What a parameter takes

Every value `.run()` returns goes back in as a parameter of its type, on every driver, so a row can be passed straight to the next statement:

| SQL type | A parameter takes |
| --- | --- |
| `smallint`, `integer` | `number` |
| `bigint` | `number`, `bigint` or a string of digits |
| `numeric` | `string` |
| `boolean` | `boolean` |
| `date`, `timestamp`, `time` | `string` |
| `timestamptz` | a `string` that names its zone |
| `json`, `jsonb` | any JSON value, or what the column's JSON Schema admits |
| `bytea` | `Uint8Array` |
| An array | an array of its element's parameter type, without `null` |
| An enum | the union of its labels |

- A `timestamptz` parameter takes the text of an instant that names its zone, as `.run()` returns it: `"2026-10-12T19:06:48Z"`, `"2026-10-12 19:06:48+09"`, `"2026-10-12 19:06:48 Asia/Tokyo"`, or `infinity`. Pass a `Date` as `date.toISOString()`. Text without a zone is refused before the statement runs, since the server would read it in the session's time zone.
- A `timestamp` or a `date` parameter refuses a `Date`: drivers write a `Date`'s time in different zones, the app's, the server's or UTC.
- A JSON parameter reaches the database as its JSON text, so a string is a JSON string: `'{"a":1}'` is stored as the string `"{\"a\":1}"`. To pass JSON text you already hold, cast it from text: `:data::text::jsonb`.
- The parameters of `limit :n` and `offset :n` are `bigint`, so they take a `number` too.

### Parameters that may be null

A parameter takes `null` in two places:

- as the first argument of `coalesce`, with a cast or without;
- written whole, with no cast, to a column that may hold `NULL`, one that is not `NOT NULL`, whose domain is not declared `not null`, and that no `check (… is not null)` holds.

```ts twoslash tab="main.ts"
import addOrder, { type Params } from "./pg_add_order.sql";
//                      ^?
```

```sql tab="pg_add_order.sql"
insert into orders (user_id, total, ships_on)
values (:user_id, :total, :ships_on)
```

A cast is the parameter's whole type, so `:email::text` never takes `null`, and a test for null (`:role is null`, `is not distinct from`) makes nothing nullable.

## Drivers

Reylo decodes the values of its own query itself, so a type parser or option you set on your client neither reaches Reylo's query nor is changed by it. Drivers differ only in what they refuse or lose:

| Driver | Refused | Lost before Reylo sees it |
| --- | --- | --- |
| `pg` | A client with `binary: true` | |
| `pg-promise` | A `receive` event that rewrites results | |
| postgres.js | A `transform.row` | |
| `Bun.sql` | | A `timestamp`'s and a `timestamptz`'s microseconds, and a date before 1 AD, which Reylo refuses |
| PGlite, Neon, `@vercel/postgres` | | |

- On `Bun.sql`, a statement with a parameter is read over the binary protocol and one without as text, so a `real` is its exact float, `1.100000023841858`, only with a parameter. Bun fails with its own error, "Failed to read data", on a `NULL` inside an `int4[]` or `float4[]`, a two-dimensional `int[]` in a statement with a parameter, and an array with explicit bounds in one without.
- The `@vercel/postgres` package is deprecated on npm: Reylo's types accept its client, and its tests do not run it.
- Each driver takes its transactions and connections too: `pg`'s Pool, Client and PoolClient; postgres.js's and `Bun.sql`'s `.begin()`, `.savepoint()` and `.reserve()`; PGlite's `.transaction()`; Neon's Pool and Client; `pg-promise`'s `.task()` and `.tx()`; and a Drizzle database's `.transaction()` and the savepoints inside it, over `pg` or postgres.js.

The type check reads the schema through postgres.js or `pg`, so an app on PGlite, Neon, `Bun.sql`, `pg-promise` or `@vercel/postgres` adds one of them as a dev dependency.

## Limits

The edges of what Reylo types on Postgres, each with what to write instead:

- **A function's body.** A SQL-language function is typed from its declaration (`returns`), never from its body, and a PL/pgSQL body is not read at all. Declare the result you return.
- **An array's dimensions and elements.** An `int[]` is `(number | null)[]` however many dimensions it holds, and its elements may be `null` unless the statement builds it from values that can't be. Keep an array one-dimensional, and filter out `null` elements before passing an array back as a parameter.
- **A row value outside JSON.** It is its text. Select its fields as columns, or build an object with `to_jsonb` or `jsonb_build_object`.
- **A statement nested past 1,000 levels** of the parse tree (about 496 terms of `a + b + …`, or 164 nested subqueries), which Reylo types from the server's description alone: any number of rows, every column nullable.
